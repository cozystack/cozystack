# Cozystack v1.7.0

Cozystack v1.7.0 adds **Proxmox VE as a substrate for tenant Kubernetes workers**, turns worker pools into first-class **`KubernetesNodes` resources**, introduces a **community Marketplace for External-Apps repositories** together with a reworked dashboard and Admin portal, extends the unified backup interface to **MongoDB, Redis, Valkey, RabbitMQ and Kafka** (plus PostgreSQL point-in-time recovery), and brings **TLS and admission-time hardening to the managed databases**. It also adds **managed Valkey**, **distributed tracing**, a **ComputePlane tenant module**, **arm64 image builds** and **slim installation variants**.

Platform components bumped in this release: **Talos v1.13.6 → v1.14.2** (DRBD 9.3.4, ZFS 2.4.4), **Cilium 1.19.5 → 1.20.2**, **KubeVirt v1.9.0** (declarative volume hotplug), **CDI v1.66.1**, **etcd-operator v0.5.6**, **Kube-OVN v1.15.26**, **CloudNativePG 1.30.0**, **Kamaji 26.9.4-edge**, **SeaweedFS chart 4.45**, **Gateway API CRDs v1.6.1**, **ingress-nginx 1.11.6**, and the build moves to **Go 1.27.1 with the Kubernetes 1.37 libraries**.

The platform migration `targetVersion` moves from **54 (v1.6.0) to 61**, so migrations **54 through 60** run as pre-upgrade hooks on the way to v1.7.0. Read the breaking-changes section before upgrading.

> **Note:** Items marked *shipped in v1.6.x* were also released in a v1.6.1–v1.6.5 patch release.

## Feature Highlights

### Proxmox substrate and `KubernetesNodes` worker pools

Managed tenant Kubernetes clusters can now run their worker VMs on an **external Proxmox VE cluster** instead of KubeVirt. A new `substrate` value on the `kubernetes` and `kubernetes-nodes` applications selects `kubevirt` (the default, unchanged) or `proxmox`. The Cluster API Proxmox provider (capmox) and the in-cluster IPAM provider ship as optional packages enabled through `bundles.enabledPackages`, and tenants on the Proxmox substrate get the Proxmox CSI driver and cloud-controller-manager so PersistentVolumes work out of the box. The tenant apiserver is published through a LoadBalancer and worker disks default to linked clones.

Worker pools are no longer an array inside the `Kubernetes` resource: each pool is now its own **`KubernetesNodes`** resource with its own health checks and its own autoscaler provision-time budget. The API accepts an edit of a pool's `spec.cluster`, but the pool's release then refuses to render it, and its `spec.storageClass` is meant to stay fixed too, though for now only the dashboard enforces that. Existing pools are adopted automatically by platform migration 56; each adopted pool rolls its worker VMs once, because the worker TalosConfigTemplate is now named by a hash of its content (#3523). New per-pool knobs include `kernelModules` for Talos (GPU pools load the NVIDIA modules automatically), CPU requests and limits, guest serial-console logging, a registry mirror for air-gapped environments, and an opt-in **golden Talos image** that CDI clones on the storage layer instead of importing the image once per worker.

### Community Marketplace and a reworked console

A new **Marketplace for External-Apps repositories** lets operators connect third-party package repositories: `cozypkg validate/init/push/tap/untap/search`, a cluster-scoped `Tap` API, keyless cosign verification through `cozypkg validate --require-signature`, and a dashboard Repositories view (now under Admin) that connects and disconnects repositories. Connecting a repository installs nothing: an operator installs its applications with `cozypkg add`, after which they appear in the catalog and their categories in the sidebars. Learn more in the [documentation](https://cozystack.io/docs/v1.7/marketplace/).

The dashboard opens on the Console, the Marketplace opens the application list directly, and tenant administration moves into an always-available **Admin portal** that shows the tenant hierarchy across every accessible tenant. Virtual machines gain a **serial console** tab and clipboard paste in the VNC console, LoadBalancer services show a connection hostname, console branding is configurable, and tenants can **import VMs from VMware vSphere** with `VMImportSource` and `VMImportTask` resources (opt-in).

### Backups for more engines, and PostgreSQL point-in-time recovery

The unified `BackupJob` / `RestoreJob` / `BackupClass` interface gains native drivers for **MongoDB** (logical backup, restore into a differently-named instance, PITR), **Redis** (and **Valkey**, through the same strategy), **RabbitMQ** (definitions) and **Kafka** (topic metadata), all bound by the `cozy-default` class, and **PostgreSQL** restores now support **point-in-time recovery** through `spec.options.recoveryTime`. Restores gained safety rails: concurrent restores are refused, a restore into another PostgreSQL major version is refused, a backup is held while its application is being restored, and each Postgres instance gets its own default WAL prefix.

### TLS for managed databases and stricter external exposure

MariaDB, RabbitMQ, MongoDB and Redis (including Sentinel) gain chart-managed or operator-managed **TLS**, the OpenSearch HTTP and Dashboards certificates of external instances now come from cert-manager, and the CA is published to tenants as a key-free `<release>.tenant-ca` trust anchor (also for NATS and Qdrant). External exposure is now fail-closed: Redis can only be exposed with TLS (Valkey has no TLS option yet and is exposed in plaintext), external PostgreSQL refuses plaintext sessions, the tenant Gateway supports TLS-passthrough listeners for native database ports (set on the `TenantGateway` resource by hand, since no chart value renders them yet), and an opt-in `networking.encryption.enabled` adds IPsec east-west encryption for the default Kube-OVN datapath.

### Distributed tracing and new managed services

Monitoring gains a **VictoriaTraces** backend with a Grafana traces datasource, a per-tenant OTLP collector, and an opt-in **shared-central** topology where tenants send spans to one store in `tenant-root` with per-tenant write-rate limits. Tracing is off by default and enabled with a `tracingStorages` entry. New managed services and modules include **Valkey** (BSD-licensed, running on the migrated freshworks-oss redis-operator), the **ComputePlane** tenant module for untrusted-code applications, an opt-in OpenEBS **LocalPV hostpath** StorageClass, `talos-log-collector`, KEDA-based **read-replica autoscaling for PostgreSQL**, a PostGIS image flavor, and Kafka **KRaft** mode with automatic in-place ZooKeeper migration.

### Multi-architecture images and slim installs

Package images now build for **linux/amd64 and linux/arm64** by default, and Talos, Harbor, the Velero KubeVirt plugin, ingress-nginx, cozy-proxy, the cozystack-scheduler and the keycloak-kms-proxy ship multi-arch releases. New **`isp-slim`, `isp-slim-generic` and `isp-hosted-slim`** installation variants install only the base platform with Cilium-only networking; applications, operators, monitoring, backups, etcd and SeaweedFS are opt-in through `bundles.enabledPackages`.

## ⚠️ Breaking Changes and Required Actions

Several changes in this release alter behavior of running clusters. Read this section before applying the v1.7.0 Platform Package. Platform migrations **54 through 60** run as pre-upgrade hooks: they adopt existing RedisFailovers onto the new operator group (54), orphan tenant FluxCD HelmReleases (55), adopt worker pools into `KubernetesNodes` (56), pin the SeaweedFS volume size limit of existing instances at 1000 (57), freeze HTTPCache on the packages artifact the cluster already runs (58), copy VMI-only hotplugged volumes into their VM spec (59), and carry each FoundationDB `cluster.version` over to the new `version` value while recording the FoundationDB, OpenSearch, Kubernetes and KubernetesNodes releases that need attention (60).

### Pre-upgrade checks and required actions

**1. Talos v1.14.2 needs `drbd_transport_tcp` (#4598).** Before upgrading a node, add `drbd_transport_tcp` to its Talos `machine.kernel.modules` next to `drbd`: Talos v1.14.2 no longer loads it on demand, and without it DRBD cannot connect to any peer. The `talm` cozystack preset from talm v0.36.0 loads it explicitly (cozystack/talm#252). Talos v1.14 also moves etcd's HTTP metrics and health endpoints from port 2379 to 2383, and the Cozystack host network policy now blocks 2383 from outside the cluster. Talos accepts a direct upgrade from v1.12.0 or later, so the v1.13 line can be skipped.

**2. Tenant Kubernetes worker pools move to `KubernetesNodes` (#3315).** `spec.nodeGroups`, `spec.nodeHealthCheck` and `spec.maxNodeProvisionTime` are removed from the `Kubernetes` resource and move to `KubernetesNodes`; existing pools are adopted on upgrade and roll their worker VMs once (#3523), and the removed fields stay accepted but ignored on upgraded clusters (editing one returns an admission warning). A pool whose release name `kubernetes-nodes-<cluster>-<pool>` would exceed 53 characters, or whose pool name a release name cannot carry, is not adopted: its objects are kept, listed in ConfigMap `cozy-system/cozystack-migration-56-unadopted`, and need to be adopted or recreated by hand. A `Kubernetes` cluster name is now capped at 32 characters. Existing pools keep their roles; a cluster that uses the `ingressNginx` addon and is created after the upgrade, or had no pool with that role, needs a `KubernetesNodes` pool with `roles: [ingress-nginx]`, otherwise the ingress controller DaemonSet schedules nothing. The `addons.fluxcd` addon is removed (#3379); tenants that had it enabled keep their running Flux release, which must be uninstalled by hand inside the tenant cluster if no longer wanted.

**3. Kamaji rolls every tenant control plane (#4398).** Updating Kamaji to 26.9.4-edge makes every tenant kube-apiserver rewrite its arguments and roll on the first reconcile, and it rolls a second time when the tenant's `kubernetes` release updates the talos-csr-signer sidecar image, which every Cozystack upgrade does; a tenant with OIDC enabled can roll a third time when the chart's own flags land. Kamaji now sets `--enable-admission-plugins` itself: the chart moves an `--enable-admission-plugins=` entry in `controlPlane.apiServer.extraArgs` into `admissionControllers`, and between the Kamaji update and the upgrade of the tenant's `kubernetes` release a tenant with such an entry runs its kube-apiserver with Kamaji's default admission plugins, which do not include NodeRestriction. Plan the upgrade window accordingly, and do not roll the Kamaji image back afterwards without checking the release notes of the PR.

**4. Cilium takes its addresses from a reserved block on Kube-OVN variants (#4778).** `networking.podCIDR` must be `/20` or wider on these variants; Cilium now uses the last `/21` of it, which Kube-OVN no longer hands out. Existing clusters move through a post-upgrade hook and each Cilium agent restarts twice (clusters on v1.6.5 already moved in that release; the restarts apply when upgrading from v1.6.4 or earlier).

**5. KubeVirt eviction and hotplug changes (#4403, #4453).** The cluster-wide eviction strategy becomes `LiveMigrateIfPossible`: VMs that cannot live-migrate (ReadWriteOnce disks, GPU or host-device passthrough) are shut down and restarted by their `runStrategy` instead of blocking a drain. A running VM keeps the old strategy until its next restart, so restart non-migratable VMs once after upgrading if their nodes need to drain. KubeVirt also runs with `DeclarativeHotplugVolumes`; migration 59 copies VMI-only volumes into `VM.spec`, which keeps them attached on tenant Kubernetes workers. On a `VMInstance` the same upgrade re-renders the VM from the chart and KubeVirt unplugs the copied volume from the running VM: before upgrading, detach such a volume inside the guest, remove it with `virtctl removevolume`, and add the disk to the VMInstance's `spec.disks` instead. At v1.6.5 a disk added to `spec.disks` attaches only at the VM's next restart; this procedure follows from the charts and has not been run on a live VM.

**6. External exposure now requires TLS (#4639, #4847, #2682).** A Redis release can only be exposed with `tls.enabled: true` (existing external instances keep working), external PostgreSQL refuses plaintext sessions unless `tls.required: false` is set, and external OpenSearch moves from the operator's CA to the chart's cert-manager CA on first reconcile (set `tls.issuer: operator` beforehand to opt out). Clients that connected with `sslmode=disable` or skipped certificate verification must be updated.

**7. Tenant route hostnames are mandatory (#3475, #3342, #4638).** An `HTTPRoute` or `TLSRoute` in a `tenant-*` namespace must declare a non-empty `spec.hostnames`; routes that relied on inheriting the listener's hostnames are rejected and must name them. Existing routes keep serving, but their next update (a Helm upgrade included) is refused until they name their hostnames. The same now applies to `GRPCRoute` (#3872). TLS-passthrough listener names are now reserved by the listener spec alone, so hostnames answered by a passthrough listener no longer get an HTTPS-terminate listener under HTTP-01.

**8. Managed PostgreSQL and MariaDB user passwords (#4078).** `users[].password` is no longer honored: passwords are always auto-generated into the `<release>-credentials` Secret. Existing releases keep their current passwords, and a `password` left in values is ignored with an admission warning. On the first reconcile after the upgrade, users that were removed from `users` while on v1.6.x but whose roles were left behind are dropped, and their objects move to `cozystack:orphaned` (#4574); clients still logging in with such a role lose access.

**9. Smaller breaking changes.** `vm-instance` now refuses `resources.cpu`, `resources.sockets` or `resources.memory` values that cannot size a VM (#4405, #4569); fix such values before the next upgrade of the release. `ApplicationDefinition.spec.release.prefix` must match `^[a-z0-9-]*$` (#3411). The multus package stages the reference CNI plugins into `/opt/cni/bin` by default; set `networking.stageCniPlugins: false` to decline (#3195); the multus resources default and the `networking.multus.resources` override are described under #4830. The FoundationDB operator no longer ships the 7.1 client, so upgrade 7.1.x clusters to 7.3 first (#4512). The HTTPCache application is removed from the catalog; instances keep working on a frozen artifact (#4200). The SeaweedFS app now defaults `master.volumeSizeLimitMB` to 400 for new instances while existing ones stay at 1000.

**10. A platform variant switch on a live cluster is refused (#4790, backport #5021).** The platform render now looks up the live `cozystack.networking` Package and fails when the variant it is about to render differs from it, because the operator deletes every HelmRelease of that Package the new variant does not install: `isp-full` to `isp-hosted` removes Cilium and Kube-OVN, `isp-full` to `isp-slim` removes Kube-OVN. The error names the value that lets the switch through, `networking.acknowledgeVariantChange: "<new variant>"` in the platform Package values; it confirms that one switch only. The guard fires on any variant change, including Talos to generic, where nothing is deleted. A cluster whose `cozystack.networking` variant was set by hand (for example `cilium-kilo`) fails the upgrade until `cozystack.networking` is listed in `bundles.disabledPackages`: acknowledging does not help there, because the render writes the bundle's variant over the manual one. Helm template, client-side dry-run and first installs are not checked.

**11. A golden-image disk into an unsuitable LINSTOR class is refused (#4796, backport #5022).** A new `vm-disk` created from a golden image is now refused at render time when CDI would CSI-clone it into a LINSTOR StorageClass that does not allow remote volume access from every node (a node-local class, for example), or when both StorageProfiles name a snapshot class that does not exist. Before, such a disk stayed pending forever without an error. Existing disks are exempt. Use the golden image's StorageClass, or have the platform administrator set the CDI `cloneStrategyOverride` to `copy` in the kubevirt-cdi package.

**12. Pod rolls on upgrade.** Besides the Kamaji and Cilium rolls above and the Redis Sentinel and data pod rolls noted under Databases and messaging, the upgrade changes the pod specs of several running workloads: every Kafka cluster rolls once because the JVM environment changes (#5019); the SeaweedFS master, volume, filer and S3 components run the in-tree patched image (#5028); the `kube-multus` DaemonSet rolls node by node to pick up its new resources (#5018); and the LINSTOR controller and satellite pods move to the rebuilt `piraeus-server` image that carries the snapshot-restore fix (#5020). Every PostgreSQL instance restarts at least once in the upgrade that moves the CloudNativePG operator from 1.28 to 1.30.0 (#3951), as a test cluster upgraded from v1.6.5 showed, and from v1.6.4 or earlier an instance with a memory limit below 512Mi and no `shared_buffers` of its own also takes the `shared_buffers` restart (#4724); a cluster with one instance is unavailable while its pod restarts. Redis data pods roll once too, one pod at a time.

**13. FoundationDB selects a release line, not a version (#5085, backport #5108).** `cluster.version` no longer selects the deployed version. A release selects its release line with `version: v7.3` (the default) or `version: v7.4`, and the platform pins the patch in `packages/apps/foundationdb/files/versions.yaml`: `v7.3` deploys 7.3.63 and `v7.4` deploys 7.4.1. Migration 60 carries each release's line over from `cluster.version`, and records a release whose patch differs from the pinned one in the `cozystack.io/migration-60-needs-attention` annotation of the `cozy-system/cozystack-version` ConfigMap. A cluster that runs another patch of its line is moved to the pinned one, downwards included: on a test cluster a 7.3.69 cluster was moved to 7.3.63, and the migration's annotation entry was the only lasting signal. A step down inside one line is a patch downgrade, which FoundationDB's [documentation](https://apple.github.io/foundationdb/administration.html#version-specific-notes-on-downgrading) does not exclude: it rules out downgrades between non-patch releases. A release whose `cluster.version` is on a line the platform no longer offers, such as 7.1, is recorded and its render is refused, so it stays on its current revision. Setting `version: v7.3` does not end that refusal while `cluster.version` still names 7.1 (on a test cluster such a release read back as `version: v7.3` and was still refused), and the operator, which no longer ships the 7.1 client, cannot move a running 7.1 cluster (#4512): move 7.1.x clusters to 7.3 before upgrading the platform. A release whose `cluster.version` is on a different line than its `version` is refused with a message that names both. The API prints no warning for `cluster.version`, and it admits an edit of a release that stores a `version` the chart does not offer; the chart refuses that value when it renders. Where platform migrations do not run, set `version` to the line each cluster runs before upgrading. Check the running patch of every FoundationDB cluster before upgrading, and read the annotation afterwards.

**14. Image overrides of Kubernetes, KubernetesNodes and OpenSearch are no longer read (#5085, backport #5108).** `images.kubectl`, `images.waitForKubeconfig` and `images.talosCsrSigner` of `Kubernetes`, `images.kubectl` of `KubernetesNodes` and `images.opensearch` of `OpenSearch` are removed, and these charts use the images the platform ships instead. A release that still carries one of them keeps the value stored, the chart ignores it, and the API shows no warning for it: on a test cluster, editing such a value through the API printed no warning about it (an edit of a `Kubernetes` resource printed only the existing `spec.nodeGroups` warning). Migration 60 lists such releases in the `cozystack.io/migration-60-needs-attention` annotation. On the first reconcile OpenSearch nodes move to the image for their selected version and Kubernetes components whose images changed restart. Before upgrading, check custom OpenSearch images: if one runs a newer version than the chart maps, switching back can leave the nodes unable to read their data. An OpenSearch release that stores `version: null` now fails to render instead of falling back to `v2`, while the API still reads it back as `v2`; set its `version`. Air-gapped installations need `docker.io` and `ghcr.io` mirrored on the management-cluster nodes.

**15. A disk still importing holds its release during the upgrade (#5087, backport #5126).** An existing `vm-disk` whose DataVolume is not ready when the platform upgrades, an import still running for example, can keep its HelmRelease in a failing upgrade and occupy one helm-controller worker until the release reconciles on its own; on a test cluster that took two failed 10-minute attempts, about 20 minutes. The cause is ordering: cozystack-controller, which copies the readiness expressions onto existing HelmReleases, starts only after the `cozystack.networking` Package is upgraded, which holds Cilium and Kube-OVN on the `isp-full` variants, and every attempt that starts before that copy waits on the DataVolume until it times out. The wait is bounded; without #5087 such a release retried without end. Finish running imports before upgrading; `kubectl get dv -A` shows the phase of every DataVolume.

**16. Read the migration log right after the upgrade.** The log of the `cozystack-migration-hook` Job in `cozy-system` carries the migrations' warnings; read it with `kubectl logs -n cozy-system job/cozystack-migration-hook` once the migrations finish. The chart keeps the Job until the next run of the hook replaces it, but on a test cluster, whose nodes had reported `DiskPressure` during the upgrade, its container log could no longer be read about 20 minutes after the run; the cause was not established. Migration 60's records are also kept in the `cozystack.io/migration-60-needs-attention` annotation, which it writes only when it recorded at least one release.

**17. Free disk space on the nodes.** Observed on a test cluster: two nodes reported `DiskPressure` during the platform upgrade and the kubelet evicted pods from one of them, so make sure the nodes have free disk space before upgrading.

### Breaking changes in this release

* **feat(opensearch)!: issue HTTP and Dashboards certificates from cert-manager**: The OpenSearch HTTP API and Dashboards already served TLS, from the operator's own private CA and with a SAN built from cluster.local while the credentials Secret advertised the release on the platform domain; for an external instance both certificates now come from a per-release cert-manager CA whose anchor the platform publishes into the tenant as <release>.tenant-ca, while an internal one keeps the operator CA unless `tls.issuer: cert-manager` is set. Any client that worked against the old endpoint was skipping verification, because no hostname it was handed could have matched that SAN ([**@Arsolitt**](https://github.com/Arsolitt) in #2682).
* **feat(multus)!: stage reference CNI plugins from the multus image**: Install the reference CNI plugins (bridge, macvlan, ipvlan, ...) into /opt/cni/bin on generic-Linux installs, where nodes do not otherwise provide them. On by default on every platform: Talos ships five of the fourteen, and the four that overlap are rewritten with the same upstream version. On generic clusters this replaces same-named files in /opt/cni/bin every time the Multus pod is recreated, so a locally managed plugin there will not survive. Set networking.stageCniPlugins: false to decline ([**@lexfrei**](https://github.com/lexfrei) in #3195).
* **feat(kubernetes)!: manage worker pools as KubernetesNodes, adopt on upgrade (Phase 2, breaking)**: Worker node pools of a managed Kubernetes cluster are now managed as separate `KubernetesNodes` resources. BREAKING: `spec.nodeGroups`, `spec.nodeHealthCheck` and `spec.maxNodeProvisionTime` are removed from the `Kubernetes` CR; pool configuration, worker health checks, and the autoscaler provision-time budget move to `KubernetesNodes`, on which the API accepts an edit of `spec.cluster` but the pool's release then refuses to render it, and `spec.storageClass` is meant to stay fixed: the dashboard does not let it change, but the API accepts an edit, and the pool then rolls its workers onto the new class. A `Kubernetes` cluster name is now capped at 32 characters ([**@IvanHunters**](https://github.com/IvanHunters) in #3315).
* **feat(gateway)!: add TLS-passthrough listeners to TenantGateway**: TenantGateway supports layer-4 TLS-passthrough listeners on native database ports for SNI-based external exposure. On HTTP-01 gateways a hostname a TLS-passthrough listener answers, including any name beneath a wildcard entry, no longer earns an HTTPS-terminate listener or a Gateway-issued certificate once a TLSRoute claiming that hostname can be served on the listener and forwards to a backend that resolves; a hostname claimed only by a TLSRoute stops earning one too. No chart value renders `spec.tlsPassthroughListeners` yet, so such a listener is set on the `TenantGateway` resource by hand. An existing TLSRoute whose hostname no passthrough listener answers stays unattached after the upgrade; remove it, or declare a `tlsPassthroughListeners` entry for its hostname ([**@lexfrei**](https://github.com/lexfrei) in #3342).
* **feat(kubernetes)!: remove FluxCD addon**: Remove the FluxCD addon (`addons.fluxcd`). It relied on AGPL-3.0 vendored charts and was disabled by default; tenant clusters that had enabled it keep their running Flux release via an automatic upgrade migration. To remove that orphaned Flux from such a tenant, uninstall its `flux-operator`/`flux-instance` Helm releases inside the tenant cluster by hand ([**@kvaps**](https://github.com/kvaps) in #3379).
* **feat(api)!: require the application release prefix to be dot-free**: `ApplicationDefinition.spec.release.prefix` must match `^[a-z0-9-]*$` (dot-free). A create, or an update that sets a new prefix, is rejected at admission when the prefix contains a dot or any other character, while an existing definition whose prefix is left unchanged is not revalidated; correct it before applying this CRD ([**@lexfrei**](https://github.com/lexfrei) in #3411).
* **fix(gateway)!: require tenant routes to declare their hostnames**: The tenant route hostname policy now requires an HTTPRoute or TLSRoute in a `tenant-*` namespace to declare a non-empty `spec.hostnames`. A route that omitted the field, or set it to an empty list, was previously admitted without any hostname being checked against the tenant apex, even though such a route inherits the hostnames of the listener it attaches to rather than matching nothing. A route in a `tenant-*` namespace relying on that inheritance is now rejected and has to name its hostnames ([**@lexfrei**](https://github.com/lexfrei) in #3475).
* **feat(postgres,mariadb)!: drop plaintext user passwords**: Passwords for managed PostgreSQL and MariaDB users can no longer be set via `users[].password` — they are always auto-generated and stored only in the `<release>-credentials` Secret, never rendered into the init-script or the SQL it runs. Existing releases keep their current passwords on upgrade; a `password` left in values is ignored with an admission warning but stays the live credential until rotated. Password rotation is deferred to a follow-up controller design ([**@scooby87**](https://github.com/scooby87) in #4078).
* **chore(platform)!: remove the HTTPCache application**: Remove the HTTPCache application from the catalog. New instances can no longer be created from the catalog and the `HTTPCache` values type is gone from the `api/apps/v1alpha1` Go module. A platform migration keeps existing instances working: on a cluster that runs one, the application is frozen on the packages artifact that cluster was already rendering from, pinned by digest, and stays manageable through the Cozystack API and the dashboard, but receives no further updates, including security updates to the nginx build. On a cluster with no instance the application is removed outright ([**@kvaps**](https://github.com/kvaps) in #4200).
* **feat(kamaji)!: update to 26.9.4-edge and read every apiServer extraArgs entry**: Update Kamaji to 26.9.4-edge. Tenant kube-apiserver arguments are now derived from a hash of the control plane's extraArgs instead of from its length, so on the first reconcile after the upgrade every tenant control plane rewrites those arguments from scratch and rolls once. The rebuilt list also orders them differently, Kamaji's own flags sorted first and the operator's kept verbatim after them, except the flags Kamaji manages itself, so the roll happens whether or not the tenant sets any extraArgs. A tenant with OIDC enabled takes a second roll when the chart's own flags land ([**@lexfrei**](https://github.com/lexfrei) in #4398).
* **fix(kubevirt)!: evict non-migratable VMs instead of blocking the drain**: VMs that cannot live-migrate no longer block a node drain. The cluster-wide eviction strategy is now LiveMigrateIfPossible instead of LiveMigrate. VMs that can migrate still migrate. VMs that cannot, for example with a ReadWriteOnce disk or GPU or host device passthrough, are shut down and started again by their runStrategy. This applies to any pod eviction, not only a drain. A VM whose disk is bound to the drained node stays down until the node returns ([**@lexfrei**](https://github.com/lexfrei) in #4403).
* **fix(vm-instance)!: refuse resources that cannot size the VM**: Resources.cpu and resources.sockets must now be positive whole numbers, and resources.memory a positive quantity. A cpu or sockets that is not a plain whole number within uint32 (for example 500m, 1k or 1.5), or a zero or negative memory, now fails at render time with an error naming the field, instead of silently becoming a one-core VM or a zero memory request. A release carrying such a value fails its next upgrade until the value is fixed. A value such as 1e1 or 2., which used to be truncated to one core, now sizes the VM with the count it spells ([**@lexfrei**](https://github.com/lexfrei) in #4405).
* **feat(kubevirt)!: drop HotplugVolumes for declarative volume hotplug**: KubeVirt now runs with DeclarativeHotplugVolumes instead of the deprecated HotplugVolumes feature gate, and kubevirt-csi no longer uses the VMI-level hot-unplug. Volume hotplug requests are applied through VM.spec. The upgrade copies volumes that older kubevirt-csi versions attached only to the VMI into VM.spec, which keeps them attached on tenant Kubernetes workers; on a `VMInstance` the same upgrade re-renders the VM from its chart and KubeVirt unplugs the copied volume (see pre-upgrade item 5). The check in the PR description is optional ([**@lexfrei**](https://github.com/lexfrei) in #4453).
* **fix(foundationdb-operator)!: drop the amd64-only 7.1 init container**: The FoundationDB operator now starts on arm64. It no longer ships the 7.1 client, because no arm64 build of it exists, so it cannot manage or upgrade a FoundationDB cluster on 7.1.x. Upgrade such clusters to 7.3 before installing this release ([**@lexfrei**](https://github.com/lexfrei) in #4512).
* **fix(vm-instance)!: refuse guest memory below KubeVirt's 1M floor**: Refuse `resources.memory` below 1M at render time, since KubeVirt does not admit a VM with less. A value above zero and below 1M rendered before and is now refused. The cpu, sockets and memory descriptions list the refused values, and the guard error marks an unquoted number as read rather than written ([**@lexfrei**](https://github.com/lexfrei) in #4569).
* **feat(talos)!: bump Talos to v1.14.2**: Bump Talos to v1.14.2, which ships DRBD 9.3.4 and ZFS 2.4.4. DRBD 9.3.4 fixes a sender thread spinning on a dead connection, two-phase-commit hangs and a data divergence after a reconnect. Before upgrading a node, add `drbd_transport_tcp` to its Talos `machine.kernel.modules` next to `drbd`: Talos v1.14.2 no longer loads it on demand, and without it DRBD cannot connect to any peer. We recommend skipping the v1.13 line and upgrading nodes straight to v1.14.2. Talos accepts a direct upgrade from v1.12.0 or later ([**@lexfrei**](https://github.com/lexfrei) in #4598).
* **feat(gateway)!: reserve a passthrough listener's name by the spec alone**: The tenant Gateway renders the api, vm-exportproxy and cdi-uploadproxy passthrough listeners only on the publishing tenant, for the names publishing.exposedServices lists while gateway.enabled is on. Under certMode http01 a name a TLS-passthrough listener answers no longer gets an HTTPS listener on 443, with or without a TLSRoute behind it. On the publishing tenant, an HTTPRoute on such a name whose TLSRoute forwards nowhere loses its listener and certificate. A TLSRoute attached by hand to a tls-* listener of another tenant loses its parent ([**@lexfrei**](https://github.com/lexfrei) in #4638).
* **feat(redis)!: refuse external access without TLS at admission**: A Redis release can be exposed outside the cluster only when it is created with `tls.enabled: true`. Creating one with `external: true` and no TLS, turning `external` on for an existing instance, or changing `tls.enabled` while `external` is on is refused at admission. Instances already external without TLS keep working and stay editable ([**@lexfrei**](https://github.com/lexfrei) in #4639).
* **fix(cilium)!: take cilium's own addresses from a block kube-ovn does not hand out**: On the kube-ovn variants cilium now takes its router and gateway api ingress ips from the last /21 of networking.podCIDR, which kube-ovn no longer hands out, so pods stop landing on addresses cilium holds. existing clusters move on upgrade through a post-upgrade hook, and each cilium agent restarts twice, once for the config change and once in the hook (clusters on v1.6.5 already moved; the restarts apply when upgrading from v1.6.4 or earlier). networking.podCIDR needs /20 or wider on these variants, and a /21 of /29s caps them at 256 nodes ([**@yankawai**](https://github.com/yankawai) in #4778, shipped in v1.6.5).
* **fix(postgres)!: refuse plaintext sessions on external instances**: An external Postgres now refuses sessions that are not encrypted. The chart renders `hostssl` rules for all users and databases with scram-sha-256 (md5 on PostgreSQL 13, matching CloudNativePG's default rule) and rejects plain `host` connections, so a client using `sslmode=disable` is refused. The new `tls.required` value follows `external` by default; set it to `false` to keep accepting plaintext sessions ([**@yrahman82**](https://github.com/yrahman82) in #4847).
* **fix(platform)!: refuse a networking variant change on a live cluster**: The platform render now refuses to change the variant of a live `cozystack.networking` Package, because the operator would then delete the CNI HelmReleases the new variant does not install (`isp-full` to `isp-hosted` removes Cilium and Kube-OVN). To go ahead, set `networking.acknowledgeVariantChange` to the new networking variant named in the error. A cluster whose variant was set by hand, such as `cilium-kilo`, needs `cozystack.networking` in `bundles.disabledPackages` before the upgrade ([**@lexfrei**](https://github.com/lexfrei) in #4790, backport #5021).
* **fix(vm-disk)!: refuse a golden-image clone CDI would leave unbound**: A new disk from a golden image is refused with a clear error when CDI would CSI-clone it into another LINSTOR StorageClass that does not allow remote volume access from every node, instead of staying pending forever; a clone that would have landed on a node already holding a replica of the golden image is refused as well. Use the golden image's StorageClass, or have the platform administrator set the CDI `cloneStrategyOverride` to `copy` in the kubevirt-cdi package ([**@lexfrei**](https://github.com/lexfrei) in #4796, backport #5022).
* **fix(kubernetes, opensearch, foundationdb)!: restrict managed application images**: Image overrides let tenants run arbitrary containers in the management cluster, including helpers with access to Talos CA secrets and Kubernetes API credentials, so the Kubernetes, KubernetesNodes and OpenSearch charts stop reading their `images.*` values and use the images the platform ships. Stored overrides are accepted without an admission warning and ignored; on the first reconcile OpenSearch nodes move to the image of their selected version and Kubernetes components whose images changed restart. FoundationDB replaces `cluster.version` with `version` (`v7.3` or `v7.4`, mapped to 7.3.63 and 7.4.1); migration 60 carries the release line over and records the releases that need attention, and the chart refuses a render whose `cluster.version` and `version` name different lines. An OpenSearch release that stores `version: null` is refused instead of rendering `v2` ([**@myasnikovdaniil**](https://github.com/myasnikovdaniil) in #5085, backport #5108).
