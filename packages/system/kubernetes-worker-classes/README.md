# Worker classes for managed Kubernetes

This package owns `cozystack.io/v1alpha1 WorkerClass`, reference reconciliation and worker-pool admission. Its CRD component installs first and retains the CRD on uninstall. Built-in `talos` and `kairos` objects are informational; custom classes are immutable and held by a finalizer while pools reference them. Admission refuses to create a pool on a new custom class, or to move a pool onto one, until the controller has added that finalizer; retry after a few seconds.

The platform forwards `kubernetesWorkerClasses.defaultWorkerClass` to this package's `defaultWorkerClass`. CREATE persists that selection; an UPDATE that omits or empties the field preserves a selected class or leaves a legacy pool legacy. The package matches KubernetesNodes CREATE and UPDATE on its served `kubernetesnodeses.apps.cozystack.io` resource in every namespace, with Exact matching, empty selectors and no matchConditions. `failurePolicy: Fail` blocks those requests if admission is unavailable, including legacy UPDATE. Existing classless Helm renders do not depend on the webhook's availability.

Certificates are issued and rotated by cert-manager. Readiness waits for the TLS listener. The pre-delete hook unregisters both admission configurations before removing their backend; a cleanup permission failure stops normal Helm uninstall rather than leaving an orphaned global Fail webhook. Force deletion or disabling Helm hooks bypasses that ordering and is not supported cleanup. Remove classified pools or restore their effective legacy Talos values before removing this package; the retained CRD does not run its finalizer controller for you.

Direct HelmRelease producers choose `workerClassName` explicitly in the effective chart values when they want class semantics. The finalizer resolves ordered Secret/ConfigMap `valuesFrom` references and inline values using the Flux chart-values helper, including `targetPath`, its Helm assignment grammar, optional missing objects/keys and final inline precedence. The reference namespace is the HelmRelease namespace, not `targetNamespace`. The webhook does not intercept raw HelmRelease writes. ComputePlane retains its classless producer contract, but its worker-chart references use the same finalizer resolver.

Deleting a custom class fails closed. While any HelmRelease in the cluster has a chart source the controller cannot trace to a Cozystack package (for example `spec.chart`, or a source object it cannot read), no custom class loses the `cozystack.io/workerclass-in-use` finalizer, and the controller log names that release as `checking pool consumer <namespace>/<name>`. Fix or remove that release; or, after confirming that no worker pool uses the class, remove the finalizer by hand.

Managed tenant charts grant `cozy-system/kubernetes-worker-classes` GET on the `cozystack-values` Secret of their own namespace, and on nothing else there, when the platform enables the managed-Kubernetes worker package. That Secret is the only `valuesFrom` source of an Application's HelmRelease, including the root tenant and ComputePlane pools in those namespaces. Existing tenants receive the grant through the shared `_cluster` values update; deletion remains blocked until that grant converges. A direct HelmRelease in a tenant namespace that takes values from any other Secret or ConfigMap needs a Role granting GET on those objects to that ServiceAccount, or its values cannot be resolved and deletion stays blocked. For a pool in an existing non-tenant namespace, the hoster must opt that namespace into `valuesNamespaces`; the default is empty and does not include `kube-system`. This creates Roles and RoleBindings, not namespaces. Each `valuesNamespaces` grant allows GET of **any Secret or ConfigMap in that namespace**, including all keys in the API response; it is not an object-name or key-level RBAC restriction. The controller reads only named references and does not list, watch or cache those objects, create grants, or acquire RBAC bind/escalate authority.

The controller also has cluster-wide GET on `cozystack.io` Packages and PackageSources, `source.extensions.fluxcd.io` ArtifactGenerators, and `source.toolkit.fluxcd.io` ExternalArtifacts. Those kind-scoped permissions are not field-level metadata restrictions. It uses the current owner UIDs, package variant/component and fixed platform source/copy chain to exclude known non-worker releases before reading their values. Unknown charts, contradictory provenance and unreadable references retain a deleting class and retry; they are operator dependencies, not evidence of zero references. Arbitrary third-party charts are not automatically recognized as non-consumers. Values-resolution errors are sanitized and referenced payloads are not logged.

Before disabling this feature, remove classified pools or restore their legacy configuration. Disable both managed-Kubernetes application packages, let the platform's shared feature flag reconcile the tenant-owned grants away, and then remove the worker package. Tenant uninstall removes its namespace grants; worker-package uninstall removes its opt-in namespace grants and unregisters its webhooks. The worker controller cannot remove tenant-owned grants on its own, and uninstalling it while the shared flag still enables those grants is not the feature-disable procedure.

## Compatibility limits

The admission update contract depends on the generic Cozystack API concurrency correction tracked in [cozystack/cozystack#5234](https://github.com/cozystack/cozystack/pull/5234). An API that refreshes a stale resourceVersion around an already admitted object can invalidate oldObject-based decisions. That correction remains outside this package.

Adopting a class is checked twice: admission compares the resolved settings, and the chart compares its render with the pool's live MachineDeployment. When the two disagree, for example because the adoption lands in the same Helm upgrade as a chart change that alters the worker templates, the release fails with the adoption message and no worker is replaced. The pool API then refuses to drop the class. As a hoster, remove `workerClassName` from the HelmRelease's inline values (pool admission does not intercept HelmRelease writes), let the classless release reconcile, and adopt the class again in an update that changes nothing else.

Kairos remains experimental. Rebuilding the platform Kairos disk from unchanged inputs can produce a different image digest. Updating the platform image reference then changes the worker template hash and replaces workers in pools using that platform image. Image reproducibility is not guaranteed. A hoster-supplied class with its own digest-pinned image does not follow platform image-reference updates; selecting a different class is a separate pool change. Baseline/override validation and successful admission do not prove worker remediation or driver support.
