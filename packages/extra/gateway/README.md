# Cozystack Tenant Gateway

Per-tenant Gateway API Gateway backed by Cilium. Installed automatically when `tenant.spec.gateway=true` on the publishing tenant. Other tenants under that tenant inherit through the publishing Gateway without opting in.

The chart renders one `gateway.cozystack.io/v1alpha1 TenantGateway` CR per tenant. The cozystack-controller reconciles the actual `Gateway`, per-tenant `Issuer`, and per-listener `Certificate` resources from there. Helm does not render `Gateway` or `Certificate` directly — that prevents the Helm-vs-controller race on `Gateway.spec.listeners` that ad-hoc HTTPRoute additions would cause.

## Inheritance: when to opt in for a separate Gateway

A tenant gets its own dedicated Gateway (own LB Service, own LB IP, own Certificate) only when it explicitly asks via `tenant.spec.gateway=true`. Every other tenant in the tree attaches its routes to the Gateway of the nearest ancestor that does own one — same shape as `_namespace.ingress` inheritance today.

The `apps/tenant` chart writes a namespace label `namespace.cozystack.io/gateway: <owner-tenant-name>` onto each tenant namespace, carrying either this tenant's own name (when owning a Gateway) or the inherited ancestor name (when inheriting). The HTTPS-terminate and port-443 passthrough listeners key their `allowedRoutes.namespaces.selector` on that label, so the same logic permits the inheriting tenant's HTTPRoutes / TLSRoutes to attach to them. The port-80 listener and the native-port listeners from `tlsPassthroughListeners` do not: both pin `kubernetes.io/metadata.name` instead, and inheritance does not reach either. cozystack-controller separately patches the same label onto every namespace in `tgw.Spec.AttachedNamespaces` so cozy-* system namespaces (cert-manager, monitoring, harbor, …) reach the publishing Gateway alongside the tenant tree, garbage-collecting labels it wrote when an entry is removed from the attach list.

Owning a separate Gateway makes sense for: a tenant that needs its own LB IP (DNS already pinned, firewall rule on a specific address), a tenant whose apex is not derived from the parent (custom `host`, e.g. `customer1.io` not under the platform apex — the ancestor's cert/Issuer can't cover it), or a tenant that wants its own ACME account / cert authority. Otherwise leave `gateway` unset and inherit.

## Cert mode: HTTP-01 (default) vs DNS-01 (opt-in) vs existing Secret

The platform-wide `publishing.certificates.solver` value selects how the controller sources TLS certificates for the tenant Gateway. Setting `publishing.certificates.wildcardSecretName` switches to a third mode (existing Secret) that overrides the solver entirely — see below.

### Default — HTTP-01

Out of the box, no extra config required. The controller:

- Renders an ACME `Issuer` in the tenant namespace with an `http01.gatewayHTTPRoute` solver pointing at the tenant's own Gateway / `http` listener.
- Watches HTTPRoutes / TLSRoutes attached to the Gateway (parentRefs pointing at it). For each unique hostname seen, it adds a per-app HTTPS listener and a per-app `Certificate` (dnsNames containing exactly that hostname).
- Per-app listener naming: `https-<first-label-of-hostname>` (e.g. `https-harbor`).
- Per-app cert naming: `<tgw-name>-<first-label>-tls`.

Adding a new published app is purely a matter of deploying its HTTPRoute — no edits to `_cluster.expose-services` needed.

### Opt-in — DNS-01

Set `publishing.certificates.solver: dns01` and configure the provider under `publishing.certificates.dns01.*` in the platform chart values. Each provider reads its own sub-block; others are ignored.

| Provider     | `publishing.certificates.dns01.provider` | Required `publishing.certificates.dns01.<provider>` keys                                  |
| ------------ | ---------------------------------------- | ----------------------------------------------------------------------------------------- |
| Cloudflare   | `cloudflare` (default)                   | `cloudflare.secretName`, `cloudflare.secretKey`                                           |
| AWS Route53  | `route53`                                | `route53.region`, `route53.secretName` (and `route53.accessKeyID` if not using IRSA)      |
| DigitalOcean | `digitalocean`                           | `digitalocean.secretName`                                                                 |
| RFC 2136     | `rfc2136`                                | `rfc2136.nameserver`, `rfc2136.tsigKeyName`, `rfc2136.secretName`                         |

The platform chart writes those values into `_cluster.dns01-*` keys consumed by the per-tenant gateway chart, which renders them onto the `TenantGateway` CR. Each provider sub-block carries safe defaults for secret-key field names (`api-token`, `secret-access-key`, `access-token`, `tsig-secret-key`) so the typical opt-in path is `solver: dns01` plus the provider-specific `secretName` (and `region` for route53 / `nameserver`+`tsigKeyName` for rfc2136).

DNS-01 mode renders a single wildcard `Certificate` covering `<apex>` and `*.<apex>`, plus the corresponding `https` (`*.<apex>`) and `https-apex` (`<apex>`) listeners. New apps published under the apex pick up the existing wildcard cert without per-listener provisioning.

For inheriting child tenants under this Gateway: the controller extends the same wildcard Certificate with `<child-apex>` + `*.<child-apex>` SANs per child, and adds one `*.<child-apex>` listener per child apex referencing the same cert. Child apex SANs are discovered by listing namespaces carrying `namespace.cozystack.io/gateway = <owner>` and reading their `namespace.cozystack.io/host` label. The ACME challenge must succeed for every SAN, which means the DNS provider account configured at the platform layer must be able to write TXT records under each child apex zone — for deeply-nested children that requires either zone delegation or a provider account with apex-spanning permissions.

Pick DNS-01 when you specifically want a wildcard cert (e.g. a long-lived staging cluster with many short-lived apps and tight LE rate limits). Otherwise stay on HTTP-01.

> **Listener-cap considerations.** Gateway API caps `Gateway.spec.listeners` at 64. In HTTP-01 mode, every published hostname adds one HTTPS listener, plus the mandatory `http` listener, one extra per TLS-passthrough service, and one per `tlsPassthroughListeners` entry on the `TenantGateway` — so a tenant approaching 60+ published apps on HTTP-01 hits the spec cap and the rendered `Gateway` fails admission. DNS-01 mode collapses every hostname under the apex into one wildcard listener and is the right choice for high-fanout single-tenant deployments.

### Opt-in — existing wildcard Secret (operator-provided)

Set `publishing.certificates.wildcardSecretName` in the platform chart values to point the tenant Gateway at a pre-existing wildcard TLS Secret instead of issuing anything via ACME. Use this when the operator already holds a wildcard certificate — purchased, or issued by a corporate CA — and wants platform services to serve under it. This mode takes precedence over `solver`: when `wildcardSecretName` is set, the solver / provider / issuer values are ignored.

The platform chart writes the value into `_cluster.wildcard-secret-name` (the name only — the certificate and private key never travel on the values channel), and the gateway chart renders `certMode: existingSecret` with `wildcardSecretRef.name` on the `TenantGateway` CR. The controller then:

- Mints no `Issuer` and no `Certificate`. Switching into this mode from HTTP-01 or DNS-01 garbage-collects the now-unused per-tenant `Issuer` and any per-listener / wildcard `Certificate` the controller previously owned.
- Renders the same single-wildcard listener shape as DNS-01: a `https` (`*.<apex>`) listener and a `https-apex` (`<apex>`) listener (plus one `*.<child-apex>` listener per inheriting child), all with `certificateRefs` pointing at the operator-supplied Secret.

The Secret must exist in the `TenantGateway`'s own namespace, be of type `kubernetes.io/tls`, and cover the apex (and `*.<apex>`). Cross-namespace references are intentionally unsupported (no `ReferenceGrant`), so each per-tenant Gateway reads the Secret from its own namespace. For the root publishing tenant that is the operator-created Secret in `tenant-root`. For a child tenant that runs its own Gateway, the platform controller replicates the operator Secret into the tenant namespace automatically — it reads the source name from the same `publishing.certificates.wildcardSecretName` that drives the consumers, so a same-named replica is mirrored into every tenant namespace that owns a termination point, then garbage-collected when wildcard mode is explicitly disabled (clearing `publishing.certificates.wildcardSecretName`) or when a tenant stops terminating TLS. A transient absence of the source Secret or the platform values channel does not prune existing replicas. No extra operator input, and the replica carries no extra RBAC — the Gateway reads only its own-namespace copy. Replication delivers the bytes, not coverage: the certificate matches a child apex only if its SAN list does, and a single `*.<apex>` does not match `*.<child-apex>`. The controller still renders a `*.<child-apex>` listener bound to the Secret for each inheriting child, so when the SANs do not cover that apex, clients of the child subdomain are served the parent certificate and see a hostname-mismatch TLS error — supply a certificate whose SANs cover the child apexes you intend to serve. Like DNS-01, this mode collapses every hostname under the apex into one wildcard listener, so it is also a way to stay clear of the 64-listener cap.

## External IP allocation

The per-tenant Gateway's auto-created `LoadBalancer` Service draws its IP from whatever LB allocator the cluster admin has configured at the platform layer — same shape as ingress-nginx today. Cozystack itself ships MetalLB installed but does not render any `IPAddressPool` / `L2Advertisement` / `BGPAdvertisement` from this chart; admins set up the allocator that suits their environment (MetalLB pool with L2 / BGP, Cilium LB-IPAM with announcer, robotlb against a cloud provider, or `Service.spec.externalIPs` pinning).

The tenant API stays mechanism-agnostic — no `gatewayIP` field, no allocator-specific manifest in the tenant chart. If a tenant needs a specific address (DNS already pinned, firewall rule, etc.), the operator pre-allocates it on the admin side: either pre-create the Service with `loadBalancerIP` set, or hand the tenant a reference to a named admin-managed pool. Per-Service IP uniqueness is the allocator's responsibility and works the same way as for any other LoadBalancer Service in the cluster.

## Layer-4 TLS passthrough on native ports

There are two distinct passthrough forms, and they do not replace each other. The `tlsPassthroughServices` chart value above renders one `mode: Passthrough` listener per named service on port 443, selected by SNI alongside the HTTPS-terminate listeners. The `tlsPassthroughListeners` field on the `TenantGateway` resource renders one listener per entry on the entry's own native port — 6379 for Redis, 27017 for a sharded MongoDB's `mongos`, 5432 for PostgreSQL where both ends are new enough to negotiate TLS directly — so a database engine can present its own certificate directly to clients on the port those clients already expect, while sharing the tenant Gateway's address. The engine has to speak TLS first: a protocol whose server opens with a plaintext greeting, MySQL and MariaDB on 3306 above all, deadlocks against a passthrough listener waiting for a `ClientHello` that never arrives, and no listener can rescue it because there is no certificate to fall back on. Which engines qualify is settled in [#2815](https://github.com/cozystack/cozystack/issues/2815) rather than here.

Each entry names a listener, a port, and an SNI hostname. The port must be free (80 and 443 belong to the Gateway's own listeners) and distinct from every other entry; the hostname must fall within the tenant apex. Those rules are enforced at admission by CEL on the CRD, so a bad entry is refused on write rather than stalling the tenant's reconcile.

No two passthrough listeners may match the same SNI, counting the port-443 listeners `tlsPassthroughServices` renders and counting wildcards — `*.<apex>` overlaps the shipped `api.<apex>` listener, so a wildcard that broad is rejected while `tlsPassthroughServices` carries its defaults. Emptying that value removes the service hostnames from the comparison but not the rule: two entries of this field still have to keep clear of each other, and a broad wildcard still covers a narrower one. Cilium selects a passthrough backend by SNI alone and cannot tell two matching listeners apart even on different ports, so the overlap would silently forward the stream to whichever one happened to win. This rule is one of those the controller checks rather than admission, so it surfaces as `Ready=False` on the TenantGateway instead of a rejected write; the type comment on `TenantGatewaySpec` carries the whole set and why each one is there.

The listener is all this field creates. Nothing is routed until a `TLSRoute` attaches to it by `sectionName: tls-<name>` and names a backend Service, and because a passthrough listener never terminates TLS, the backend — not the Gateway — must hold the certificate for the listener's hostname. Route attachment is bounded more tightly than on the other listeners, in two ways: only `TLSRoute`, and only from the publishing tenant's own namespace, pinned by the `kubernetes.io/metadata.name` label that kube-apiserver writes. `TLSRoute` alone is what the pinned Cilium derives from the `TLS` listener protocol rather than something Gateway API guarantees: the spec leaves the protocol-to-kind mapping to the implementation and its own table pairs `TLS` with `TCPRoute` as well. The kind is left to the protocol rather than spelled out because at the pinned `v1.19.5` a listener that spells its kinds out has them applied to every route on the Gateway, not to itself; `v1.19.6` matches the listener the route actually names, so this one is a patch bump away from being unnecessary rather than tied to the rest of the pin. The `namespace.cozystack.io/gateway` label the port-443 listeners select on is stamped on every inheriting child tenant namespace, which is a reasonable attach set for a shared HTTPS port and a poor one for a database port. Narrowing is free while no chart value exposes this field; widening later is a values change, whereas narrowing after something depends on it would not be.

Three current limitations are worth knowing before designing around this, and they do not share an origin. Two follow from the Cilium version this platform pins: the field is refused outright when `certMode` is `dns01` or `existingSecret`, because those modes serve the whole tenant from one `*.<apex>` terminate listener whose SNI match covers every hostname this field can declare, and a hostname a passthrough listener answers gets no HTTPS-terminate listener even when the two would sit on different ports, which includes every name beneath a wildcard entry rather than only the name written in the spec. The third is a deliberate narrowing of this phase and not a pin consequence: each entry must occupy its own port, so two instances of the same engine cannot both sit on the engine's native port distinguished only by SNI. Gateway API permits that pair and the port-443 `tls-<svc>` listeners already are that pair; the restriction exists because nothing downstream yet makes two engines on one port testable, and lifting it means deleting a check in the controller and the matching CEL rule in the CRD, without touching a field or a type. The two pin-derived restrictions should be revisited when the pin moves; the narrowing is independent of it. All three are validation changes with no API impact.

Two more things belong next to those, because both bear on what a tenant sees. The first is what withdrawing the terminate listener does for the pin itself: in HTTP-01 mode it removes the HTTPS-terminate and TLS-passthrough pair that used to sit on port 443 under one SNI for `api`, `vm-exportproxy` and `cdi-uploadproxy`. Upstream states beside `NeedsCrossProtocolSplit` that same-port HTTPS and TLS-passthrough conflicts cannot be fixed by per-port listeners and have to be rejected before translation, so an HTTP-01 Gateway carrying that pair is a Gateway a later Cilium refuses. The `dns01` and `existingSecret` modes still carry it, because the wildcard `https` listener overlaps `tls-api` by SNI on the same port and nothing here changes that. The second is a shape this platform has not run before: a passthrough listener declared with no `TLSRoute` behind it. `TenantGateway` readiness folds in every listener's `Accepted` and `Programmed` conditions, so if Cilium declines to program a listener nothing routes to, declaring an entry ahead of its route would take the tenant's `Ready` to false. Whether it does is not something this change establishes.

The reason the pin matters is worth stating plainly, because it also decides what the declared port does and does not buy. On `v1.19.5` the whole Gateway is translated into a single Envoy listener with a TLS inspector in front, and every filter chain is selected by transport protocol and SNI alone: `toFilterChainMatch` in `operator/pkg/model/translation/envoy_listener.go` sets no destination port. A terminate chain and a passthrough chain carrying one name therefore land in the same listener whichever Gateway port declared them, which is where both pin-derived restrictions come from. The same fact has a consequence that is not a restriction: the declared port is where the listener is published, not where the backend can be reached. A TLS handshake carrying `postgres.<apex>` selects that passthrough chain on any port the tenant's load balancer forwards, port 443 included, so narrowing a firewall to 80 and 443 does not put the engine out of reach. The hostname is the access surface; give the backend its own authentication and treat the SNI as public. Cilium `v1.19.6` restores the port boundary, but conditionally, and only for a listener something actually routes to. `NeedsPerPortListeners` is true when the model has more than one HTTPS port, or more than one TLS-passthrough port carrying a route, or an HTTPS chain and a routed passthrough chain on different ports sharing an SNI. A passthrough listener with no `TLSRoute` behind it contributes no filter chain, so it counts toward none of the three, which is consistent: with no route there is nothing on that port to collide with anything. Once a route attaches, a tenant that also keeps any of the shipped `tlsPassthroughServices` has two routed passthrough ports and the listeners split on the second clause. A Gateway whose only routed passthrough listener is that single entry splits on the third clause instead, and only when a terminate chain shares its SNI, which is precisely the pair these restrictions exist to prevent. So the criterion for lifting them is not the pin alone: it is the pin together with a configuration the split actually covers.

This field is set on the `TenantGateway` resource directly; the chart exposes no corresponding value yet. That matters operationally, though not the way it first looks: the `TenantGateway` is rendered and owned by this chart, but helm-controller runs with drift detection off here (no HelmRelease in the tree sets `spec.driftDetection`, and the controller carries no feature gate for it), so a `kubectl edit` adding `tlsPassthroughListeners` is not reverted on the release's next interval. Nor does the next `helm upgrade` take it away. Helm patches a custom resource whose Go type it does not know with a two-way merge between the old rendered manifest and the new one, computed by `jsonpatch.CreateMergePatch(oldData, newData)` in `pkg/kube/client.go`, and the live object is not consulted at all on that path. A key the chart renders in neither manifest therefore appears in no patch and is never removed. `helm uninstall`, a chart that starts rendering the key, and `spec.upgrade.force` are the ways out, and nothing in this tree sets the last of them. So the hazard runs the other way from the usual one: a hand-added entry is not something the platform will quietly revert, it is a native database port published on the tenant's shared address that stays published until somebody removes it by hand. Until the chart exposes a value, treat the field as reachable only for experimentation, and write down what you added.

One behaviour change reaches clusters that never set this field. A hostname a route claimed used to earn an HTTPS-terminate listener and an ACME certificate even when a passthrough listener already held that hostname, and the certificate went to a hostname whose backend presents its own. On port 443 that also put two listeners on one port and hostname — Gateway API admits the pair, because its listener uniqueness rule counts the protocol as well as the port and hostname, and its compatibility rules then call for both to report `Conflicted`. In HTTP-01 mode a hostname a passthrough listener holds now produces neither listener nor certificate, and neither does a hostname only a `TLSRoute` claims. Overlap is symmetric, so it also runs the other way: an `HTTPRoute` publishing `*.<apex>` overlaps the shipped `api.<apex>` entry and loses the whole wildcard, not the one name inside it. HTTP-01 cannot issue a wildcard certificate in the first place, so the route was never going to be served under that name; what changes is that it is now told. That covers both passthrough forms: the port-443 one, where Gateway API would mark the pair `Conflicted`, and the native-port one, where the pinned Cilium erases the port boundary in translation and leaves the same collision one layer down. The other two cert modes are unaffected, because neither renders per-hostname listeners at all: the wildcard `https` and `https-apex` listeners still cover every name under the apex, passthrough hostnames included, so nothing changes and nothing is shed there. On HTTP-01 the shipped `tlsPassthroughServices` default is `api`, `vm-exportproxy` and `cdi-uploadproxy`, each with a platform `TLSRoute` attached, so a stock Gateway-enabled cluster sheds three terminate listeners on upgrade and the controller garbage-collects the three certificates that went with them. Read that as a change of serving path, not only as the removal of something idle: before the upgrade each of those hostnames has both listeners on port 443, Gateway API calls for both to report `Conflicted`, and which one answers a given connection is not something the spec tells you, so on the pinned Cilium you cannot know from the objects whether `api.<apex>` is being terminated by the Gateway or passed through to the backend. After the upgrade it is passed through, always. If anything in your cluster depends on the Gateway terminating one of those three names, it depends on the half of that ambiguity that goes away. Read the Gateway's listener conditions before upgrading if you want to know what those listeners were doing on your cluster rather than what the spec says they should have been doing.

If something does depend on that terminate path, there are three ways forward and they are not equivalent. Moving the consumer to another hostname under the apex costs nothing: a name outside `tlsPassthroughServices` still earns its own terminate listener and ACME certificate, while the passthrough name goes on answering the platform's own `TLSRoute`. Switching `certMode` to `dns01` or `existingSecret` keeps the pre-upgrade shape wholesale, since neither mode renders per-hostname listeners and the wildcard covers passthrough names along with everything else, at the price of DNS-01 credentials or an operator-supplied certificate, and both modes refuse `tlsPassthroughListeners` outright. Removing a service from `tlsPassthroughServices` does not bring its terminate listener back, and that is the point worth reading twice: the passthrough listener goes, the platform `TLSRoute` that attached to it by `sectionName: tls-<svc>` has nothing left to attach to, and the hostname is then claimed by a `TLSRoute` alone, which earns no terminate listener either. Nothing serves the name until something else claims it. So this path is a rewrite rather than a rollback, and it is only finished once the component is republished by an `HTTPRoute` on that hostname, which does earn a terminate listener and a certificate. For `api` that is the Kubernetes API endpoint, and passthrough means its clients hold a TLS session with the apiserver itself; terminating in front of it changes what that session authenticates against, so check what your clients present before picking this one.

Schema constraints tightened alongside this field reach objects that already exist, and every one of them is a kind the apiserver ratchets. `apex` is bounded at 253 characters, and `tlsPassthroughServices` at 62 entries each a DNS-1123 subdomain of at most 249 characters; a stored value that violates one still passes any write that leaves it unchanged, and the rule bites only once the value itself changes. `apex` gets no format pattern, deliberately, and that is not a statement that a mixed-case host works. It arrives verbatim from the `namespace.cozystack.io/host` label, which nothing normalizes and which may hold upper case, and the controller then composes listener hostnames from it that Gateway API refuses, so such a tenant's Gateway does not render with or without a pattern here. What a pattern changes is only where that lands: refused at the write it fails this HelmRelease and everything the release owns, admitted it is `Ready=False` on the one Gateway. An apex no listener hostname can sit within is reported by the controller instead, and only when `tlsPassthroughListeners` is in use. A repeated `tlsPassthroughServices` entry is reported by the controller as `Ready=False` rather than refused at admission, and that is deliberate, though not for the reason symmetry suggests. Ratcheting does reach a list-type error, and at a coarser grain than the rest: the apiserver checks an incoming object's list-type semantics only when the stored object passes them, for the whole object at once (read from `pkg/registry/customresource/strategy.go` in the pinned `k8s.io/apiextensions-apiserver` v0.35.0). So declaring the list a set would not block writes to an object already carrying a duplicate; it would stop every list on that `TenantGateway` from being checked at all, silently, while the duplicate the controller can name goes on being reported by name. The shipped defaults and the chart's own `fail` on an empty host conform to all of it, so an upgrade is a no-op in practice.

## Security model

Tenants in Cozystack interact with the platform exclusively through `apps.cozystack.io/*` resources (Tenant, Bucket, Kubernetes, …) served by `cozystack-api`. Tenant RBAC (`cozy:tenant:*` aggregated to a RoleBinding in the tenant's own namespace) does not grant write access to `gateway.networking.k8s.io/*`, core `Namespaces`, or `cozystack.io/Package`. Every layer below is shaped by that constraint — the security model is built around the `apps.cozystack.io/*` API surface, not around Gateway API admission.

The protections below split into three groups by who they defend against:

- **Tenant-user-input gates** — Layer 4 (`cozystack-tenant-host-policy`). `Tenant.spec.host` is the user-supplied field that surfaces as a security boundary at the hostname layer; it is gated on every Create / Update via `cozystack-api`'s admission chain (`pkg/registry/apps/application/rest.go`).
- **Defense-in-depth** — Layers 1, 2, 5, 6, 7, 8. These do not protect against tenant-user input (tenants don't hold the relevant RBAC). They guard against bugs in cozystack-controller / Flux, supply-chain compromise of an app chart that emits Gateway API or Ingress resources, and confused-deputy mistakes by a cluster admin. Fail-closed via `failurePolicy: Fail` + `validationActions: [Deny]`. Layers 1-7 cover the opt-in Gateway API dataplane; Layer 8 covers the legacy Ingress dataplane, which is the default (Gateway API is off by default).
- **Admin-against-themselves** — Layer 3 (`cozystack-gateway-attached-namespaces-policy`). Rejects a `kubectl edit packages.cozystack.io` that would slip a `tenant-*` entry into the platform Package's `gateway.attachedNamespaces`. Layer 6 catches the same misconfiguration at helm render time.

1. **Namespace whitelist on listeners.** Every listener carries an `allowedRoutes.namespaces.from: Selector`, but the two listener classes select on different labels. The plain-HTTP listener (port 80) pins an explicit `kubernetes.io/metadata.name` allow-list (written by kube-apiserver, unspoofable) covering only the tenant namespace itself (where the controller-owned http→https redirect HTTPRoute lives) and `cozy-cert-manager` (HTTP-01 ACME challenge HTTPRoutes) — so app HTTPRoutes attaching by hostname cannot bind to port 80 and serve plaintext. The HTTPS-terminate listeners and the port-443 TLS-passthrough listeners select on `namespace.cozystack.io/gateway` instead, while the native-port layer-4 listeners from `tlsPassthroughListeners` use the same `kubernetes.io/metadata.name` pin as port 80, naming only the publishing tenant's namespace. That label has two writers, and the second is the one to keep in mind when sizing the blast radius: the controller stamps it on the publishing tenant's namespace and on each `gateway.attachedNamespaces` entry from the platform chart (default includes the `cozy-*` namespaces for platform services and `default` for the Kubernetes API TLSRoute), and the tenant chart stamps it on **every inheriting child tenant namespace**, pointing at the nearest ancestor that owns a Gateway. So the attach set is not just the tenant plus admin-listed namespaces — it is the whole inheriting tenant subtree. A namespace without the label cannot attach any `HTTPRoute` or `TLSRoute` to those listeners, but a child tenant receives it automatically at creation rather than by patching anything. Which route kinds a listener admits is settled two different ways. On port 443 it is written out: HTTPS-terminate and `tls-<svc>` passthrough listeners alike carry `HTTPRoute` and `TLSRoute` together, because divergent kind sets on one port make Cilium merge the listeners and drop HTTPRoutes (cilium#45559). The native-port listeners from `tlsPassthroughListeners` name no kinds at all and let Gateway API derive them from the listener protocol, which for TLS is `TLSRoute` — naming that kind explicitly is what the pinned Cilium turns into a rejection of every HTTPRoute on the Gateway, whatever port the listener sits on. Both ways exclude GRPCRoute, TCPRoute and UDPRoute, so nothing attaches outside the route-hostname VAP's coverage.
2. **`cozystack-gateway-hostname-policy`** — `ValidatingAdmissionPolicy` on `gateway.networking.k8s.io/v1 Gateway` CREATE/UPDATE. Reads `namespaceObject.metadata.labels["namespace.cozystack.io/host"]` and rejects any listener hostname that is not equal to that value or a subdomain of it. `matchConditions` gate the VAP to cozystack-managed namespaces only — Gateways in unrelated namespaces (e.g. `kube-system`) are not touched.
3. **`cozystack-gateway-attached-namespaces-policy`** — VAP on `cozystack.io/v1alpha1 Package` CREATE/UPDATE. Rejects any `tenant-*` entry in `spec.components.platform.values.gateway.attachedNamespaces`. Catches direct `kubectl edit packages.cozystack.io` that would bypass the helm render-time guard in layer 6.
4. **`cozystack-tenant-host-policy`** — VAP on `apps.cozystack.io/v1alpha1 Tenant` CREATE/UPDATE. Rejects setting or changing `spec.host` unless the caller's groups contain `system:masters`, `system:serviceaccounts:cozy-system`, `system:serviceaccounts:cozy-cert-manager`, `system:serviceaccounts:cozy-fluxcd` or `system:serviceaccounts:kube-system`. Closes the path where a tenant user sets `spec.host=dashboard.example.org` on their own tenant to have the tenant chart write a hijacked label into the namespace.
5. **`cozystack-namespace-host-label-policy`** — VAP on core `v1 Namespace` CREATE/UPDATE. Rejects any set or change of the `namespace.cozystack.io/host` label, except by the same trusted-caller whitelist as layer 4. This closes both first-time label writes on CREATE and first-time adds on UPDATE — only cozystack/Flux service accounts (which apply the tenant chart) can stamp the label.
6. **Render-time `fail` in cozystack-basics.** The cozystack-basics chart fails the helm render if `_cluster.gateway-attached-namespaces` contains any `tenant-*` entry. Triggers on the helm-install path before the cluster ever sees the values — complements layer 3 which triggers at `kubectl apply` time.
7. **`cozystack-route-hostname-policy`** — VAP on `gateway.networking.k8s.io/v1 HTTPRoute` and `v1alpha2 TLSRoute` CREATE/UPDATE. Scoped to `tenant-*` namespaces (cozy-* are cluster-admin-managed and trusted to publish under any apex). Rejects any `spec.hostnames` entry that is not equal to the namespace's `namespace.cozystack.io/host` label or a subdomain of it. Defense-in-depth against an app chart bug or supply-chain compromise that emits Gateway API resources outside the tenant's apex — tenants in Cozystack do not hold `gateway.networking.k8s.io/*` RBAC by design, so this is not a tenant-user defense. The within-apex cross-namespace case (a tenant chart claiming a hostname that is published by a `cozy-*` app) is handled by the controller at reconciliation time: when two routes from different namespaces claim the same hostname, the `cozy-*` namespace wins and the loser receives a `HostnameConflict` condition under the controller's name in `Status.Parents`. Which condition a route gets follows the shape of the refusal. `HostnameConflict` says another route holds the name. `NoMatchingListenerHostname` says there is no listener this route can attach to, which is three shapes and the message tells them apart: nothing renders the name at all; the only listener carrying it is a TLS-passthrough listener, which answers the SNI but is not something an `HTTPRoute` attaches to, and no terminate listener was rendered beside it; or the route named a listener in its `parentRef` and that listener answers a different hostname. Read it as "nothing here will serve you", not as "no listener exists": in the last two shapes the listener is right there, and on port 443 the passthrough one even lists `HTTPRoute` among its kinds. The third shape is also the one that can hit a route inside the publishing tenant, which is why it is not folded into the namespace refusal below. `NotAllowedByListeners` is the third condition and the case Gateway API defines that reason for: a native-port listener answers the name and would take the route's kind, and admits routes only from the tenant's own namespace, so a route from elsewhere is refused by a listener that would otherwise serve it. All three hold whether or not another route also claimed the name. Two `TLSRoute`s racing for a hostname a passthrough listener answers, both eligible to attach, still get the conflict, because that listener serves exactly one of them. A route carrying a conflict alongside any of the others is reported as `HostnameConflict`, with every cause spelled out in the message: the reason names the half an operator can act on by moving the other route. Read `Accepted=False` here as "at least one of this route's hostnames is not served", not as "this route serves nothing": Gateway API gives one condition per parentRef while a route may claim several hostnames, so a route claiming one withdrawn name and one ordinary name keeps the listener and the certificate for the second. The message names the hostnames that lost, and the ones it does not name are being served.
8. **`cozystack-ingress-hostname-policy`** — VAP on core `networking.k8s.io/v1 Ingress` CREATE/UPDATE. Gateway API is opt-in and **off by default**, so in the default configuration tenant applications publish through a legacy Ingress on the shared ingress-nginx; layers 1-7 constrain tenant hostnames on the opt-in Gateway path, and this VAP adds a hostname constraint on the default Ingress path. Scoped to `tenant-*` namespaces (cozy-* are cluster-admin-managed and trusted). A hostname on `spec.rules[].host` or `spec.tls[].hosts[]` is allowed when it is within the namespace's own `namespace.cozystack.io/host` apex, OR when it lies entirely outside the platform root apex (`_cluster.root-host`) — the second case lets a tenant route its own external custom domain (for example the `kubernetes` app's Proxied `addons.ingressNginx.hosts`, which routes a user-supplied domain to a nested cluster). A hostname that falls under the platform root apex but outside the namespace's own apex is rejected; a rule with no host (an unbounded catch-all) and `spec.defaultBackend` (a catch-all for unmatched traffic) are also rejected. Fail-closed: a `tenant-*` namespace missing its host label is denied, and the policy renders only when `_cluster.root-host` is set. This bounds which apexes a tenant Ingress may claim under the platform domain; it does not attempt to resolve every possible hostname collision.

For `tenant-root` the allowed host suffix is `publishing.host`; for any `tenant-<name>` that inherits from its parent the suffix is `<name>.<parent apex>`. A child tenant with an independent apex (`customer1.io` instead of a subdomain) is handled correctly because the VAP reads the per-namespace label rather than assuming a subdomain hierarchy.

## Rate limits

cert-manager issues per-listener `Certificate` resources in HTTP-01 mode (one per published app), or a single wildcard `Certificate` per tenant in DNS-01 mode. With `issuerName: letsencrypt-prod` (the default), every certificate counts against the [Let's Encrypt rate limits](https://letsencrypt.org/docs/rate-limits/):

- 50 new certificates per registered domain per week.
- 5 duplicate certificates per week for the same set of hostnames.
- 300 new orders per account per 3 hours.

A cluster where many tenants share the same apex domain can exhaust these quickly, especially in HTTP-01 mode where each published app contributes one certificate. Mitigations:

- Use `publishing.certificates.issuerName: letsencrypt-stage` for non-production clusters (staging does not count against prod quotas).
- Limit the number of simultaneous tenant Gateways per cluster via the platform's package quota, or cap it via `tenant.spec.resourceQuotas` with `count/certificates.cert-manager.io` to limit how many `Certificate` objects a tenant may create.
- Switch to DNS-01 to consolidate every tenant's apps under one wildcard cert (cuts cert count from N apps to 1).
- For bare-metal or air-gapped deployments consider an internal ACME server or the self-signed `ClusterIssuer` (`selfsigned-cluster-issuer`) that ships alongside the Let's Encrypt issuers.

Recommended tenant-level quota to contain a misbehaving tenant:

```yaml
apiVersion: apps.cozystack.io/v1alpha1
kind: Tenant
spec:
  gateway: true
  resourceQuotas:
    count/certificates.cert-manager.io: "10"
```

The default for a fresh tenant is unlimited; operators running shared-apex multi-tenant clusters should set this explicitly (or stage it via the tenant-application default values) before opening `gateway: true` to non-trusted tenants.

## Known limitations

- **Upstream application gaps** — some chart-level features (harbor ACL integrations, bucket upstream limitations) remain on ingress-nginx workflows in upstream docs; cozystack tracks those separately as upstream PRs.
- **Supported ACME issuers** — `publishing.certificates.issuerName` for Gateway-based tenants must be `letsencrypt-prod` or `letsencrypt-stage` (the controller maps those names to concrete ACME server URLs). To support another ACME provider, extend the controller's renderer with an additional branch.
- **DNS-01 wildcards require DNS provider access for every apex level** — when a deeply nested tenant (e.g. `tenant-root` → `alice` → `alice-prod`) inherits DNS-01 mode, the parent's `*.alice.example.org` SAN requires the parent's ACME challenge to write a TXT record under `_acme-challenge.alice.example.org`. If the operator hasn't delegated that subzone to the parent's DNS provider account, cert issuance for the grandchild apex stalls. HTTP-01 mode is unaffected — each per-listener challenge runs against the specific hostname.
- **Cilium sharing-key port-collision** — operators wanting *multiple* per-tenant Gateways to share a single LB IP cannot do so on current Cilium: every tenant Gateway claims `443/TCP`, so `lbipam.cilium.io/sharing-key` is inactive on port collision ([cilium#21270](https://github.com/cilium/cilium/issues/21270), [cilium#42756](https://github.com/cilium/cilium/issues/42756)). Each Gateway → own LB IP until Cilium ships ListenerSet. Within a single Gateway, inheritance (parent + all inheriting children sharing one IP) works today.
- **Upstream application gaps** — some chart-level features (harbor ACL integrations, bucket upstream limitations) remain on ingress-nginx workflows in upstream docs; cozystack tracks those separately as upstream PRs.
- **Supported ACME issuers** — `publishing.certificates.issuerName` for Gateway-based tenants must be `letsencrypt-prod` or `letsencrypt-stage` (the controller maps those names to concrete ACME server URLs). To support another ACME provider, extend the controller's renderer with an additional branch.
