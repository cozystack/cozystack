# site-router VyOS appliance image lifecycle

This note records where the `site-router` gateway VM's boot image comes from, what it must carry, and the rule that keeps the image and its first-boot configuration in sync. It is the provenance record for `packages/system/vyos-router-image`, the package that builds the appliance and publishes it as the digest-pinned containerDisk each gateway boots from.

## What the image is

The gateway boots from a **VyOS 1.5-rolling** qcow2 appliance disk. VyOS rolling releases are date-stamped snapshots (`1.5-rolling-YYYY.MM.DD`); the exact snapshot is pinned when the artifact is published (see T14 below). VyOS is a Debian-derived, GPL-licensed router OS and is freely redistributable, so cozystack can host and republish its own copy.

The appliance disk carries three things baked in so it boots unattended under KubeVirt:

- **NoCloud cloud-init datasource** — KubeVirt seeds first-boot configuration via a `cloudInitNoCloud` volume, so the image must honor the NoCloud datasource (the prebuilt appliance also ships the OpenNebula datasource, which is harmless under KubeVirt).
- **cloud-init `write_files`** — first-boot config (interfaces, management firewall, and the management-API seed) is applied from NoCloud user-data. The seed is delivered as a `write_files` of a complete, VyOS-serialized `config.boot`, deliberately **not** the VyOS-native `vyos_config_commands` module nor a `runcmd` script — see [Config delivery](#config-delivery-why-write_files-and-why-cloud-init-at-all) below.
- **VyOS HTTPS API** — enabled in the image so the controller can push configuration to the running gateway once it is reachable.

## How it is consumed (Phase 1)

Consumption is via CDI, matching how every other OS image in the catalog is consumed:

- Each gateway's boot `DataVolume` imports the digest-pinned OCI containerDisk directly, via CDI's registry importer (`source.registry`, `docker://…@sha256:…`). A registry containerDisk rather than an HTTP qcow2 is what makes the boot disk pinnable by digest — CDI's HTTP importer cannot verify a `sha256`.
- The import is per instance. A shared golden PVC in `cozy-public` would be the cheaper import, and earlier revisions of this feature tried both routes, but it cannot be advanced: CDI populates a `DataVolume` only at creation, so a new digest cannot replace an existing golden's contents, and every later gateway would keep booting the previous appliance while its cloud-init contract had already moved on. Importing per instance keeps the disk and the digest that produced it in lockstep.

The digest lives in `packages/apps/site-router/images/vyos-router-disk.tag`, stamped there by the `image` target of `packages/system/vyos-router-image` — the same cross-package stamp the talos build makes into `bootbox/images/matchbox.tag`. `site-router.applianceDiskUrl` is what consumes that stamp: it hands CDI the digest alone, dropping the tag because CDI's `docker://` transport cannot parse a reference carrying both (`Docker references with both a tag and digest are currently not supported`), and it fails the render loudly on a `.tag` that is empty or carries no `@sha256:` digest rather than importing a reference that cannot resolve. `hack/image-refs-no-placeholder.bats` fails the build if a placeholder (all-zero) digest is ever committed, because that shape satisfies every check above while resolving nowhere.

**The committed reference is currently digest-less — `…/vyos-router-disk:v0.0.0` — and that is deliberate, not an oversight.** A first-party image that has never been built has no digest to commit, and nothing in the PR lane can create one: `build-vyos` uploads its stamp as a patch fragment and never commits, so only the first release build (`tags.yaml` → `make build` → `Prepare release`) can land a real `ref@digest`. The alternative, committing an all-zero placeholder, is strictly worse and is what `image-refs-no-placeholder.bats` exists to reject: it looks like a valid pin, satisfies every shape check the chart makes, and then resolves nowhere at import time. This is the same state `site-router-controller:v0.0.0` is in in this very PR, and the same state `securitygroup-controller:v0.0.0` sat in on `main` for four weeks until the v1.6.0-rc.4 build stamped it to `v1.6.0@sha256:09ee1d8f…`. Note that `docs/agents/image-refs.md` says a bare tag must not be committed and already names `securitygroup-controller:v0.0.0` as a live exception to its own rule; this is a second one, knowingly taken, on the same terms and for the same duration. Two consequences worth knowing while it lasts: the ref is invisible to `hack/lib/image-refs.sh` (it greps for `@sha256:`), so the promote, retag and mirror tooling skip the appliance until it is stamped, and the chart does not render in-tree at all, because a digest-less reference is exactly what `site-router.applianceDiskUrl` refuses — so `tests/dv_test.yaml` asserts that refusal, and the rendered URL, storageClass and 12Gi request are asserted instead by `hack/site-router-appliance-ref.bats`, which writes a stamped `.tag` into a copy of the chart before rendering. Move them back into the helm-unittest suite once the first release build has stamped a real digest.

This deliberately does **not** go through `packages/system/vm-default-images`. That package is opt-in (rendered only when listed in `bundles.enabledPackages`) and is a catalog of user-selectable OS images — neither fits a platform-owned appliance disk that one app requires in order to boot at all. A tenant who got the SiteRouter catalog entry on a default install would find its boot disk cloning a PVC that does not exist. Nor does it go through a dedicated golden package of its own: that removes the opt-in problem but adds two others, since an operator naming only that package in `bundles.disabledPackages` would strand the app's registration on an unresolvable dependency, and the golden still could not be advanced in place. Importing from the registry per instance needs no package, no `dependsOn` edge and no shared object in `cozy-public` at all.

Advancing the appliance needs no operator step beyond the bump itself: a new digest in the `.tag` is what the next gateway imports. Existing gateways keep running on the disk they already imported and take the new appliance only when their instance is recreated, which is the tunnel-dropping restart described below.

## How an update propagates

Two kinds of change reach a running gateway, and only one of them drops the tunnel.

**Day-2 configuration changes do not restart the VM and do not drop the tunnel.** The controller pushes the rendered VyOS configuration over the live HTTPS management API (`POST /configure`) as a single atomic transaction, so a change to `remoteCIDRs`, static routes, BGP or the tunnel parameters is applied in place; a no-op reconcile (config hash unchanged) makes no HTTP call at all. Established IPsec SAs survive a configuration push.

**An image change restarts the VM, which is the one routine tunnel-dropping operation.** Bumping the boot image means re-importing the VM disk from the new appliance digest and restarting the gateway VM. A VM restart tears down every running IPsec SA, so the tunnel is down from the moment the VM stops until it reboots, cloud-init re-seeds the base configuration, the controller re-pushes the live configuration, and the remote peer re-establishes (the gateway is the responder, so the remote peer must re-dial). No day-2 configuration change causes this — only an image (or VM template) change does. Plan an image bump as a maintenance window for the affected tunnels.

Because the boot image and its first-boot cloud-init are a matched pair (see the invariant below), an image bump also re-runs first-boot cloud-init. The `cloudInitSeed` value is mixed into the VM firmware UUID: change it to force a first-boot cloud-init re-run, or clear it to preserve an existing VM's UUID (and skip the re-run) across a re-render that does not intend to reconfigure from scratch.

## Provenance and the no-internal-infra rule

The appliance is now built reproducibly in-repo (see the section below), so the committed default is a **cozystack-owned** artifact with no dependency on private infrastructure. No internal or third-party hosting URL for the appliance appears anywhere in this repository; the committed reference is a cozystack-owned OCI containerDisk under the `cozystack/cozystack` GHCR namespace, held in `vyos-router-disk.tag`. Which registry a build actually pushes to is the build's own, not this reference's: the PR lane sets `REGISTRY` to OCIR (`iad.ocir.io/…`, see `.github/workflows/pull-requests.yaml`) and pushes there under a `pr-<N>-<sha>` tag, while GHCR is the `REGISTRY ?=` default that a release build uses. So `build-vyos` does not publish the committed GHCR reference — a release build does.

## T14 — reproducible in-repo build (pipeline landed)

The reproducible in-repo build is implemented in `packages/system/vyos-router-image`: a pinned `vyos-build` flavor (`flavors/vyos-router.toml`) produces the qcow2, `hack/build-qcow2.sh` drives the pinned build container, and the `Makefile` `image` target packages the qcow2 as a KubeVirt containerDisk, pushes it, and stamps the digest into the consuming chart's `packages/apps/site-router/images/vyos-router-disk.tag`. The `build-vyos` job in `.github/workflows/pull-requests.yaml` runs it in CI and carries the stamped digest into the installer artifact via the patch-fragment mechanism — as an uploaded artifact only. That job ends at `git diff --binary HEAD > _out/fragments/vyos.patch`; it never commits and never pushes, so the stamp reaches e2e through `pr.patch` and never reaches the branch. The only step in this repository that commits a digest is the `Prepare release` commit in `tags.yaml`, which runs `make build` on a release tag, post-merge. Unlike `build-talos`, which runs on every non-docs PR because e2e needs the Talos disk regardless, `build-vyos` is path-gated to the VyOS image pipeline and its consumers and is skip-tolerant: it is a ~60-minute privileged live-build against an upstream apt mirror that floats, so making every unrelated PR depend on it would trade broad CI reliability for nothing. On a release, `make build` runs it like every other image build (root `Makefile`), stamping the release's own digest.

Two of the pins in that `Makefile` (`VYOS_BUILD_IMAGE`, `VYOS_BUILD_REF`) have Renovate custom managers in `.github/renovate.json`; `VYOS_VERSION` has none and is a manual bump, taken together with the cloud-init contract below. Do not read those managers as a guarantee the pins cannot age. Renovate only evaluates the default branch, so neither manager sees this package until it merges, and even afterwards they raise a PR rather than holding anything up — while `VYOS_BUILD_REF` going stale is a hard build failure on the upstream mirror's kernel-retention clock, not on Renovate's. `VYOS_BUILD_REF` fell behind exactly this way before the package ever landed. The Makefile comment block above the pins carries the detail and the verification commands.

The flavor bakes the conformance fixes the reused (stripped) appliance lacked — a working cloud-init (NoCloud datasource forced, so `write_files` seeds first boot), the HTTPS REST API server, `/var/log/nginx`, and eth0-over-DHCP as an image default — plus a baked `config.boot.default` (the cloud-init VyOS module aborts without one; vyos.dev/T7206). The pins are the `vyos-build` container digest and git ref plus the snapshot version label; the upstream rolling apt mirror floats, so the build is pinned-inputs / best-effort-reproducible, not bit-identical.

Two things remain a **maintainer action**, both requiring a CI run (a push, gated to the maintainer): (1) a green `build-vyos`, which proves the pinned inputs still build and puts a real digest in front of e2e through the patch fragment — the committed reference stays digest-less until the first release build stamps it, for the reasons given above, so this is not a pre-merge commit step; (2) the empirical boot-conformance proof (cloud-init applies the seed, the HTTPS `/configure` REST answers, eth0 has a DHCP address, nginx serves :443, the firewall seed is applied), which the parked site-router e2e performs once the image is published.

`build-vyos` is also the pin's only real watcher, and it is path-gated and skip-tolerant, so a PR that does not touch the VyOS pipeline will not notice a stale `VYOS_BUILD_REF`. See the comment block above the pins in `packages/system/vyos-router-image/Makefile` for what Renovate does and does not cover here.

## Config delivery: why `write_files`, and why cloud-init at all

The first-boot seed is delivered as a cloud-init `write_files` that drops a complete, VyOS-serialized `config.boot` at `/opt/vyatta/etc/config/config.boot`, **not** via the VyOS-native `vyos_config_commands:` key and **not** via a `runcmd` script. This is forced by the stripped cloud-init module set on the pinned image, established empirically across three boot-conformance iterations on image `sha256:a3bfc9fe…` (2026-07): (1) `vyos_config_commands:` (the `cc_vyos_userdata` module) is enabled but serializes single-value leaf nodes into `config.boot` as the invalid braced `node { value }` instead of the valid inline `node "value"`, so boot-time activation rejects the whole file; (2) `runcmd:` / `bootcmd:` never run because `cloud_final_modules` is empty on this image; (3) `write_files` is the one config-capable module actually enabled (cloud_config stage), it runs before the `vyos-router` activation, and the file it drops is what gets activated — validated hands-off (config activates clean, eth0 DHCPs, the HTTPS API answers on :443 with the seeded key). The `config.boot` template base was captured verbatim from VyOS's own `save`, so its serialization is correct by construction; the chart substitutes only host-name, the api-key and managementCIDR. Do not hand-edit the tree into `node { value }` form and do not switch back to `vyos_config_commands:` / `runcmd:` without re-verifying the module set and serializer on the then-pinned image. The authoritative copy of this note lives next to the template in `templates/_helpers.tpl`.

Shipping the whole `config.boot` (not just a seed) means the chart now owns every baked default that must survive first boot — the locked `vyos` login (`encrypted-password "*"`) with no `service ssh`, the ttyS0 console, and the `// vyos-config-version:` / `// Release version:` footer that pins the config to the image build (a mismatch triggers a VyOS config migration that can reformat or reject the file). These are asserted in `tests/secret_cloudinit_test.yaml` and, being image-specific, are the sharpest edge of the atomic-advance invariant below.

cloud-init is required for the bootstrap even though the controller configures the gateway over the API: the controller's HTTPS `/configure` channel can only answer once the gateway already has an IP, the API running, and the per-instance api-key installed — it cannot bootstrap itself. cloud-init NoCloud user-data (a per-instance Secret) is the idiomatic KubeVirt channel for that day-0 step. The only cloud-init-free alternative — bootstrapping via qemu-guest-agent `guest-exec` — reopens a remote-exec surface on a deliberately-locked-down appliance (no SSH, login locked) and needs `guest-exec` RBAC plus the KubeVirt feature gate plus a security review; it was a deliberate Phase-1 non-goal.

## Invariant — image and cloud-init advance atomically

The boot image and the first-boot cloud-init it consumes are a matched pair: the config schema, the management-API seed layout, and any VyOS-version-specific config syntax or cloud-init behavior are tied to the exact image snapshot. Whenever the pinned image reference changes, the cloud-init contract must be re-validated and advanced in the same change — never bump one without the other. Treat the image digest and the cloud-init template as a single unit that moves together. Concretely: because the chart now ships the whole `config.boot` (captured from the image's own `save`), an image bump requires re-capturing `config.boot` from the new image and updating the `// vyos-config-version:` / `// Release version:` footer — not merely re-testing a seed.
