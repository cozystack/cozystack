# site-router VyOS appliance image lifecycle

This note records where the `site-router` gateway VM's boot image comes from, what it must carry, and the rule that keeps the image and its first-boot configuration in sync. It is the provenance record for `packages/system/vyos-router-image`, the package that builds the appliance and publishes it as the digest-pinned containerDisk each gateway boots from.

## What the image is

The gateway boots from a qcow2 appliance disk derived from a published **VyOS Stream** image — currently `2026.03`, from the `circinus` release train, on a Debian bookworm base. Stream is VyOS's quarterly technology preview of the upcoming LTS: the images are public, signed, and **archived**, so a pin stays fetchable rather than rotting. VyOS is a Debian-derived, GPL-licensed router OS and is freely redistributable, so cozystack can host and republish its own copy.

This replaced a full live-build against `packages.vyos.net/repositories/rolling`, and the reason is worth recording because it is not going to change. That repository keeps only the *current* kernel and republishes without warning, while vyos-build raises `kernel_version` before the matching kernel is published — so a pin was unbuildable both when it aged and, briefly, when it was fresh. On 2026-09-08 the retention clock took the pinned kernel away between one build and the next: `E: Unable to locate package linux-image-6.18.48-vyos`, hours after that exact package had built successfully. The per-release and LTS repositories that would have fixed this are not open to the public (`repositories/circinus` and the dated `releases/circinus/...` snapshot the image's own `sources.list` names both answer `403`), so there was no repository to move to — only a way to stop needing one.

What that costs, stated plainly: **no VyOS package can be added to the appliance.** Whatever upstream cut is what there is. Anything the appliance needs on top must come from Debian, which the image is built on, or be a plain file. `packages/system/vyos-router-image/hack/inject-appliance.sh` is where that happens, and it is the appliance's real recipe now.

The stock Stream image is not usable as-is under KubeVirt, so the build adds four things:

- **A serial console on ttyS0** — the only piece still contributed by the vyos-build flavor, through `boot_settings`, because `create_raw_image` reads it even under `--reuse-iso`. Without it `virtctl console` is silent.
- **The appliance seed** — a systemd unit that installs the per-instance `config.boot` from the NoCloud disk before `vyos-router` reads it. This replaces cloud-init, which the Stream image does not carry; see [Config delivery](#config-delivery-the-appliance-seed) below.
- **`qemu-guest-agent`** — so the VMI reports `AgentConnected` and is introspectable. It is a Debian package and never was on any VyOS repository; it and its one missing dependency (`liburing2`) install offline from the frozen Debian archive.
- **`/var/log/nginx`** — nginx is the `:443` HTTPS-API listener the controller drives, and it does not start without its log directory.

## How it is consumed (Phase 1)

Consumption is via CDI, matching how every other OS image in the catalog is consumed:

- Each gateway's boot `DataVolume` imports the digest-pinned OCI containerDisk directly, via CDI's registry importer (`source.registry`, `docker://…@sha256:…`). A registry containerDisk rather than an HTTP qcow2 is what makes the boot disk pinnable by digest — CDI's HTTP importer cannot verify a `sha256`.
- The import is per instance. A shared golden PVC in `cozy-public` would be the cheaper import, and earlier revisions of this feature tried both routes, but it cannot be advanced: CDI populates a `DataVolume` only at creation, so a new digest cannot replace an existing golden's contents, and every later gateway would keep booting the previous appliance while its configuration contract had already moved on. Importing per instance keeps the disk and the digest that produced it in lockstep.

The digest lives in `packages/apps/site-router/images/vyos-router-disk.tag`, stamped there by the `image` target of `packages/system/vyos-router-image` — the same cross-package stamp the talos build makes into `bootbox/images/matchbox.tag`. `site-router.applianceDiskUrl` is what consumes that stamp: it hands CDI the digest alone, dropping the tag because CDI's `docker://` transport cannot parse a reference carrying both (`Docker references with both a tag and digest are currently not supported`), and it fails the render loudly on a `.tag` that is empty or carries no `@sha256:` digest rather than importing a reference that cannot resolve. `hack/image-refs-no-placeholder.bats` fails the build if a placeholder (all-zero) digest is ever committed, because that shape satisfies every check above while resolving nowhere.

**The committed reference is currently digest-less — `…/vyos-router-disk:v0.0.0` — and that is deliberate, not an oversight.** A first-party image that has never been built has no digest to commit, and nothing in the PR lane can create one: `build-vyos` uploads its stamp as a patch fragment and never commits, so only the first release build (`tags.yaml` → `make build` → `Prepare release`) can land a real `ref@digest`. The alternative, committing an all-zero placeholder, is strictly worse and is what `image-refs-no-placeholder.bats` exists to reject: it looks like a valid pin, satisfies every shape check the chart makes, and then resolves nowhere at import time. This is the same state `site-router-controller:v0.0.0` is in in this very PR, and the same state `securitygroup-controller:v0.0.0` sat in on `main` for four weeks until the v1.6.0-rc.4 build stamped it to `v1.6.0@sha256:09ee1d8f…`. Note that `docs/agents/image-refs.md` says a bare tag must not be committed and already names `securitygroup-controller:v0.0.0` as a live exception to its own rule; this is a second one, knowingly taken, on the same terms and for the same duration. Two consequences worth knowing while it lasts: the ref is invisible to `hack/lib/image-refs.sh` (it greps for `@sha256:`), so the promote, retag and mirror tooling skip the appliance until it is stamped, and the chart does not render in-tree at all, because a digest-less reference is exactly what `site-router.applianceDiskUrl` refuses — so `tests/dv_test.yaml` asserts that refusal, and the rendered URL, storageClass and 12Gi request are asserted instead by `hack/site-router-appliance-ref.bats`, which writes a stamped `.tag` into a copy of the chart before rendering. Move them back into the helm-unittest suite once the first release build has stamped a real digest.

This deliberately does **not** go through `packages/system/vm-default-images`. That package is opt-in (rendered only when listed in `bundles.enabledPackages`) and is a catalog of user-selectable OS images — neither fits a platform-owned appliance disk that one app requires in order to boot at all. A tenant who got the SiteRouter catalog entry on a default install would find its boot disk cloning a PVC that does not exist. Nor does it go through a dedicated golden package of its own: that removes the opt-in problem but adds two others, since an operator naming only that package in `bundles.disabledPackages` would strand the app's registration on an unresolvable dependency, and the golden still could not be advanced in place. Importing from the registry per instance needs no package, no `dependsOn` edge and no shared object in `cozy-public` at all.

Advancing the appliance needs no operator step beyond the bump itself: a new digest in the `.tag` is what the next gateway imports. Existing gateways keep running on the disk they already imported and take the new appliance only when their instance is recreated, which is the tunnel-dropping restart described below.

## How an update propagates

Two kinds of change reach a running gateway, and only one of them drops the tunnel.

**Day-2 configuration changes do not restart the VM and do not drop the tunnel.** The controller pushes the rendered VyOS configuration over the live HTTPS management API (`POST /configure`) as a single atomic transaction, so a change to `remoteCIDRs`, static routes, BGP or the tunnel parameters is applied in place; a no-op reconcile (config hash unchanged) makes no HTTP call at all. Established IPsec SAs survive a configuration push.

**An image change restarts the VM, which is the one routine tunnel-dropping operation.** Bumping the boot image means re-importing the VM disk from the new appliance digest and restarting the gateway VM. A VM restart tears down every running IPsec SA, so the tunnel is down from the moment the VM stops until it reboots, the appliance seed re-installs the base configuration, the controller re-pushes the live configuration, and the remote peer re-establishes (the gateway is the responder, so the remote peer must re-dial). No day-2 configuration change causes this — only an image (or VM template) change does. Plan an image bump as a maintenance window for the affected tunnels.

Because the boot image and its first-boot cloud-init are a matched pair (see the invariant below), an image bump also re-runs first-boot cloud-init. The `cloudInitSeed` value is mixed into the VM firmware UUID: change it to force a first-boot cloud-init re-run, or clear it to preserve an existing VM's UUID (and skip the re-run) across a re-render that does not intend to reconfigure from scratch.

## Provenance and the no-internal-infra rule

The appliance is now built reproducibly in-repo (see the section below), so the committed default is a **cozystack-owned** artifact with no dependency on private infrastructure. No internal or third-party hosting URL for the appliance appears anywhere in this repository; the committed reference is a cozystack-owned OCI containerDisk under the `cozystack/cozystack` GHCR namespace, held in `vyos-router-disk.tag`. Which registry a build actually pushes to is the build's own, not this reference's: the PR lane sets `REGISTRY` to OCIR (`iad.ocir.io/…`, see `.github/workflows/pull-requests.yaml`) and pushes there under a `pr-<N>-<sha>` tag, while GHCR is the `REGISTRY ?=` default that a release build uses. So `build-vyos` does not publish the committed GHCR reference — a release build does.

## T14 — reproducible build (pipeline landed)

The build lives in `packages/system/vyos-router-image`. `hack/build-qcow2.sh` fetches the pinned Stream ISO and verifies its digest, then runs vyos-build's `build-vyos-image --reuse-iso` inside the pinned container to install that ISO onto a disk image; `hack/inject-appliance.sh` then adds everything the stock image lacks; and the `Makefile` `image` target packages the qcow2 as a KubeVirt containerDisk, pushes it, and stamps the digest into the consuming chart's `packages/apps/site-router/images/vyos-router-disk.tag` — the same cross-package stamp the talos build makes into `bootbox/images/matchbox.tag`.

`--reuse-iso` short-circuits live-build entirely: in `build-vyos-image` the whole branch that reads `packages`, `includes_chroot` and `default_config` is skipped, and only `create_raw_image` runs afterwards. So the flavor contributes exactly three settings that still reach the image — `image_format`, `disk_size` and `boot_settings` — and everything it used to declare has been removed from it rather than left to mislead. The injection step assembles the same overlayfs VyOS assembles at boot (a read-only squashfs under `/boot/<version>/` with an overlay upper directory beside it) and works inside it, so the squashfs is never rebuilt.

The pins are in the `Makefile`: the Stream release and its ISO digest, the two Debian packages with their digests, and the vyos-build container and git ref. Two of them have Renovate custom managers in `.github/renovate.json`; `VYOS_STREAM_RELEASE` deliberately does not, because VyOS publishes Stream as a page rather than a feed and a manager pointed at a datasource that does not exist is worse than a manual pin. None of these can now age into a build failure the way `VYOS_BUILD_REF` did — the artifacts they name are archived, not rotated.

The `build-vyos` job in `.github/workflows/pull-requests.yaml` runs the build in CI and carries the stamped digest into the installer artifact via the patch-fragment mechanism, as an uploaded artifact only. That job ends at `git diff --binary HEAD > _out/fragments/vyos.patch`; it never commits and never pushes, so the stamp reaches e2e through `pr.patch` and never reaches the branch. The only step in this repository that commits a digest is the `Prepare release` commit in `tags.yaml`, which runs `make build` on a release tag, post-merge. Unlike `build-talos`, which runs on every non-docs PR because e2e needs the Talos disk regardless, `build-vyos` is path-gated to the VyOS image pipeline and its consumers and is skip-tolerant.

## Config delivery: the appliance seed

The per-instance configuration is a complete, VyOS-serialized `config.boot` carried verbatim as the NoCloud `user-data`, and installed at `/opt/vyatta/etc/config/config.boot` by a systemd unit baked into the image (`packages/system/vyos-router-image/overlay/vyos-appliance-seed.sh`), ordered `Before=vyos-router.service` so the file is in place before VyOS reads it.

There is no cloud-init in this appliance, and there cannot be: the module set the chart needs is VyOS's fork, and that lives only in a repository which is not public, while the Stream image ships no cloud-init at all. This turned out to cost nothing, because the chart's entire use of cloud-init had already collapsed to a single `write_files` entry — the VyOS-native `vyos_config_commands:` module serialized single-value leaf nodes as the invalid braced `node { value }`, and `runcmd:`/`bootcmd:` never ran because `cloud_final_modules` was empty. Reproducing one file copy in twenty lines of shell removes the dependency instead of working around it. KubeVirt still renders the `cloudInitNoCloud` volume, so the transport is unchanged; only the thing that reads it moved into the image.

Shipping the whole `config.boot` means the chart owns every baked default that must survive first boot — the locked `vyos` login (`encrypted-password "*"`) with no `service ssh`, the ttyS0 console, and the `// vyos-config-version:` / `// Release version:` footer that pins the config to the image build. These are asserted in `tests/secret_cloudinit_test.yaml` and, being image-specific, are the sharpest edge of the atomic-advance invariant below.

A seed is still required even though the controller configures the gateway over the API, and the reason is a chicken-and-egg the API cannot break on its own: the controller's HTTPS `/configure` channel only answers once the gateway has an IP, the API running, **and** the per-instance api-key installed. That key is what the seed carries, which is also why it cannot be baked into the image. The one seed-free alternative — bootstrapping through `qemu-guest-agent` `guest-exec` — reopens a remote-exec surface on a deliberately locked-down appliance and needs `guest-exec` RBAC plus the KubeVirt feature gate plus a security review; it remains a deliberate non-goal.

Diagnostics travel separately. When `_logSerialConsole` is set (a platform-and-suite switch the aggregated API refuses from a tenant), the chart renders a second Secret and attaches it as its own `cozydiag` disk, which the same seed unit installs. Its own disk on purpose: the `config.boot` is captured verbatim from VyOS `save`, and a diagnostics payload that broke it would leave the guest unconfigured and unreachable — the very outage the diagnostics exist to explain.

## Invariant — image and configuration advance atomically

The boot image and the `config.boot` it is seeded with are a matched pair: the config schema, the management-API seed layout, and any VyOS-version-specific syntax are tied to the exact image. Whenever the pinned image changes, the configuration contract must be re-validated and advanced in the same change — never bump one without the other.

Concretely, because the chart ships the whole `config.boot`, an image bump requires re-capturing it from the new image and updating the `// vyos-config-version:` / `// Release version:` footer, not merely re-testing a seed. The footer is the release's own component-version map, and it is what decides whether VyOS migrates the config, reformats it, or rejects it outright. The authoritative way to obtain it is a `save` on the new image; it can also be read off the image without booting, by taking the highest migration step in each directory under `/opt/vyatta/etc/config-migrate/migrate/`, which is the same source `vyos.component_version.version_info_from_system()` reads.

Worth knowing before the next bump: moving from `1.5-rolling` to Stream `2026.03` moved several components *backwards* (`bgp@8`→`@6`, `system@33`→`@31`, `policy@9`→`@8`, `qos@3`→`@2`), because a quarterly Stream cut is older than the rolling tip. The rolling-era `config.boot` did migrate cleanly onto `2026.03` when tested, but a config claiming component versions newer than the image's is not a state to leave in place — restamp the footer as part of the bump.
