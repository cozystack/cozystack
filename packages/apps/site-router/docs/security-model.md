# site-router security model (Phase 1)

This note records the Phase-1 security boundary of the `site-router` app: what each guard defends, where it is enforced (guest VyOS firewall vs. Cilium pod policy vs. kube-ovn vs. the aggregated apiserver), why the guest source filter is mandatory, and the residuals that are deferred to tracked follow-ups. It mirrors the design's Security section and is accurate to what is implemented in this repository. The VyOS firewall syntax the guards use has been validated live against the shipped image — the `firewall ipv4 {input,forward} filter` / `firewall ipv4 name <NAME>` family and the `ipsec match-ipsec-in` / `ipsec match-none-in` matchers — so it is no longer provisional; the one residual that still needs a booted gateway is the runtime negative-security e2e proof, called out below.

The gateway is a router VM that terminates an IPsec tunnel and L3-forwards decrypted traffic onto the tenant pod network. That makes it deliberately more privileged than an ordinary tenant pod — it must source packets that are not its own pod IP, and it must be reachable from the public internet on the tunnel ports. The guards below re-contain that privilege so a compromised or misconfigured tunnel cannot become tenant-crossing, node-reaching, metadata-stealing or open internet egress.

## Threat model in one line

A remote peer (or anything that can spoof its source) sends traffic through the tunnel; the gateway must forward only traffic that is sourced from a declared remote network AND destined for the tenant's own cluster networks, must never let tunnel traffic reach the cluster's management/metadata surfaces or unrelated tenants, and must expose only the tunnel responder ports to the world while keeping its management API reachable by the platform controller alone.

## kube-ovn port_security — full relaxation + the mandatory guest source filter

OVN's per-port `port_security` drops any packet whose source IP/MAC is not the port's own — which is exactly what a router must do (it forwards packets with the remote client's preserved source IP, not the gateway pod IP). kube-ovn v1.15.10 cannot scope a CIDR in allowed-address-pairs, so Phase 1 relaxes `port_security` **fully** on the gateway VM port only (`ovn.kubernetes.io/port_security: "false"`).

**Where the relaxation is set (validated live, kube-ovn v1.15.10).** kube-ovn reconciles the logical-switch-port `port_security` field only at pod **creation** — flipping the annotation on an already-wired, live virt-launcher pod does **not** reconcile the OVN port (confirmed empirically). The relaxation is therefore **baked onto the VM pod template** (`spec.template.metadata.annotations` in `templates/vm.yaml`), so the virt-launcher pod is born with it and the OVN port is created relaxed. The controller **verifies** the pod carries the baked annotation — it no longer patches it live (a live patch would have no OVN effect) — and a finalizer's best-effort cleanup still removes it on delete.

Full relaxation removes OVN's anti-spoof for that one port, so the guest **tunnel-ingress source filter is the compensating control and is mandatory** — it is not optional hardening. Relaxing the port with no source guard would let the gateway spoof arbitrary cluster source addresses. Because that trust boundary depends on the guest, the chart always renders the boot disk as the platform's digest-pinned appliance. That is a property of the chart, not of RBAC: a tenant SUPER-ADMIN holds `kubevirt.io virtualmachines` with verb `*` (`cozy:tenant:super-admin:base`), so they can edit the gateway VirtualMachine directly — swap the cloud-init secretRef for inline userData, and the appliance seed installs whatever it names on the next boot. The bootloader lock does not cover that path, because it never reaches the bootloader. See the residuals.

**The D8-ordering tradeoff (Phase-1 posture, security-relevant).** In the earlier design the controller physically held `port_security` enforcing until it had confirmed the guest source filter was live, and re-enforced it if the filter later dropped (D8: never relax before the guard is up). Because the relaxation must now be baked at pod creation, that dynamic ordering is no longer physically possible: **the port is relaxed from boot, before the controller confirms the guest source filter**. The consequences:

- The guest source filter — installed on the controller's first config push — is the **sole** compensating control. There is no OVN-level backstop while it is absent.
- There is a **boot window** between pod creation and the first successful config push during which the port is relaxed with no guest guard. This window is bounded by the fact that the tunnel is not yet up in it — there is no decrypted (spoofable) tunnel traffic to forward until the controller has pushed the tunnel config, and that same push installs the source filter.
- The controller's D8 gate degrades from a physical control to a **reconciliation progression** check: it still confirms the source filter is live before completing a successful reconcile, and if the filter later drops it re-establishes it by invalidating the cached config hash and re-pushing (the source filter, not `port_security`, is what it maintains). It no longer toggles `port_security`, because a live toggle has no OVN effect on this kube-ovn version.

Scoped `port_security` (a kube-ovn CIDR allowed-address-pair that would let the port keep anti-spoof for everything except the declared remote networks, removing the need to relax fully) remains the tracked follow-up that would close this window; see the residuals below.

The source filter lives in the guest as a VyOS named rule set (`TUNNEL-INGRESS`): it accepts established/related return traffic, then one accept per `(declared remoteCIDR × tenant-reachable destination)` pair, and drops everything else by default. Each accept matches **source ∈ remoteCIDR AND destination ∈ a pod IP or Service ClusterIP owned by this tenant namespace**. The controller lists that namespace's own Pods and Services and represents each pod IP and each ClusterIP as a `/32`; it deliberately admits neither the whole cluster pod CIDR nor the whole cluster service CIDR — the first would let a remote peer reach every other tenant's workloads on the flat pod network, the second would expose permitted platform ClusterIPs. Gateway pods, terminating pods, completed Job/CronJob pods and hostNetwork pods (whose reported pod IP is a node address) are excluded from the set, and because the set is enumerated per reconcile a pod created between two reconciles becomes reachable from the remote site on the next successful push rather than immediately. The destination constraint is load-bearing: a jumped-chain accept in VyOS is a terminal verdict, so a source-only accept would forward a valid-source packet to ANY destination — including the public internet — turning the gateway into unintended egress and bypassing the forward default-deny. A valid-source packet to the world or another non-cluster destination matches no accept and falls through to the default drop; a destination inside this tenant's own pod/ClusterIP set proceeds to Cilium. Cross-tenant isolation is structural in the guest rather than delegated to Cilium: a pod IP belonging to any other namespace is in no accept rule, so the same default action drops it. It has to be enforced here, because Cilium does not deny it — the tenant baseline (`packages/apps/tenant/templates/networkpolicy.yaml`) admits `fromEntities: [world, cluster]` on an empty endpoint selector, and the deny-set forces every `remoteCIDR` to be non-cluster, so the decrypted packet's preserved source always classifies as identity `world`, which that baseline permits. With no remotes declared the rule set still emits the established/related accept and the default drop, so a resolved tunnel with an empty `remoteCIDRs` fails **closed** (drops all decrypted traffic except return), never open. An empty DESTINATION set fails the same way and for a while did not: it used to degrade each accept to source-only, which is the world-egress hole this constraint exists to be, guarded by nothing but a comment asserting the controller could never resolve an empty set on a pushing path. It could — the set is built from this namespace's live Pod IPs and Service ClusterIPs, and in a namespace holding only the gateway, the tunnel Service disappearing between the LoadBalancer read and the Service list empties it. The renderer now emits no new-flow accept at all in that state and the controller records a Warning Event naming it, so the tunnel carries return traffic only until the next push resolves a real set.

## Forward default-deny and the IPsec-match jump

The guest forward chain is default-deny (`firewall forward default-action drop`). Routed mode advertises specific remote networks and never a default route, so forwarding is denied unless a packet matches a recognised flow: established/related return traffic is accepted, **non-IPsec** traffic (locally-originated, pre-encryption tenant→remote egress) is accepted so the source filter never black-holes a tenant's own outbound flow, and **IPsec-decrypted** ingress jumps to the `TUNNEL-INGRESS` source filter above. This IPsec-match structure is the M2 redesign of an earlier design that bound the source filter to the pod-NIC inbound hook and wrongly dropped locally-originated egress; matching on the IPsec-decrypted property instead scopes the source filter to decrypted-from-tunnel traffic only.

## Two-boundary management-API isolation

The VyOS management API (HTTPS 443) must be reachable by the platform controller and by nothing else — not by the tenant, not by the remote peer over the tunnel. The appliance ships with **no SSH service and the well-known `vyos` login locked** (`encrypted-password "*"`), so there is no network shell to reach: the pod-network NIC is reachable by any same-namespace tenant workload, and a baked SSH service + the shipped `vyos`/`vyos` credential would have let any such workload SSH in and reconfigure the gateway outside the controller. The HTTPS API is therefore the only management surface, and the management firewall opens only 443 (not 22). There is no debug shell. The earlier revision of this document said console access was "gated by cluster RBAC", which was true only in the sense that some RBAC governs it: the RBAC in question is `cozy:tenant:use:base`, which grants `virtualmachineinstances/console`, `virtualmachineinstances/vnc` and `virtualmachines/restart` with no `resourceNames`, and `packages/apps/tenant/templates/tenant.yaml` binds it in every tenant namespace — which is where a SiteRouter instance lands. The tenant holds it, and the platform hands them the kubeconfig to use it (`packages/extra/info`). So the console is assumed reachable by the tenant, and what makes that safe is the guest, not the API permission.

- **Boundary A — guest local-input drop on IPsec-decrypted traffic.** A packet the gateway decrypts and addresses to itself never crosses the pod veth where Cilium enforces, so Cilium cannot see it. The guest therefore drops, as the first local-input rule, any IPsec-decrypted packet destined for ports 22/443. It matches the IPsec-decrypted property (not an interface), so it covers every tunnel interface with one rule. The **controller** emits it on every push independently of `_managementCIDR` (gated only on a resolved tunnel device), so on any path where a tunnel exists it is present for the life of that tunnel. The **first-boot seed** is narrower: the chart seeds the guard set inside its `_managementCIDR` block, so the escape hatch (`_allowOpenManagement=true` with an empty `_managementCIDR`) boots with no firewall at all — Boundary A included — until the controller's first push installs one. That unguarded window is why the hatch is test-only, and `secret_cloudinit_test.yaml` asserts the absence explicitly rather than leaving it implied.
- **Boundary B — Cilium gateway-ingress policy.** A namespaced `CiliumNetworkPolicy` selecting the gateway endpoint makes it ingress-default-deny-except-listed at the pod boundary: it admits only the public IPsec responder ports (UDP 500/4500) from the world and the controller's identity (namespace `cozy-site-router`, app `site-router-controller`) on TCP 443. The API port is never world-open.

The management firewall itself (guest local-input chain) accepts established/related return traffic, then the HTTPS API (443) only from `_managementCIDR` (SSH 22 is never opened — the appliance has no SSH service), then IKE/NAT-T/ESP when a tunnel is configured and per-peer BGP (TCP 179) when BGP is enabled, and drops everything else. It is fail-closed: an empty `_managementCIDR` aborts rendering unless `_allowOpenManagement=true` is set explicitly (a test-only escape hatch), enforced identically in the chart (the boot seed) and in the controller (`--management-cidr` / `--allow-open-management`). The firewall is seeded at first boot so the API is protected before it is reachable, and re-stamped by the controller on every push. The `_managementCIDR` value and the controller flag MUST agree (both default to the kube-ovn pod CIDR `10.244.0.0/16`); a drift silently locks the controller out of the router.

Both keys are platform-injected and carry the `_` prefix precisely so "test-only" is a property of the API rather than a sentence in this document. They used to be ordinary tenant parameters in `values.schema.json`, which meant a tenant could set `_allowOpenManagement`'s predecessor on their own instance and boot a gateway with no firewall at all. The aggregated API rejects every top-level `_` key from a tenant on Create and Update, the same mechanism that gates `_logSerialConsole`. What this costs is the schema's IPv4-CIDR pattern, which no longer validates the value; `site-router.assertSafeVyOSInputs` keeps that check in the template, where it was already present as defence in depth and is now the only layer.

## Bootloader lock — the console is not a way in

The console is assumed tenant-reachable (see above), and the whole Phase-1 posture depends on the guest holding the line, so every path from that console to a root shell has to be closed inside the image. Two exist in stock VyOS and neither needs a credential. The generic one is GRUB's interactive entry editor, reachable with `e` — and the flavor deliberately puts GRUB on ttyS0 so boot output lands on `virtctl console`, which puts the editor there too. The specific one is worse: upstream's `data/templates/grub/grub_options.j2` ships a **"Boot options" submenu whose "Password reset" entry boots `init=/usr/libexec/vyos/system/standalone_root_pw_reset`** and whose "System recovery" entry boots `init=/usr/bin/busybox init`. That is a root shell in two menu selections, with nothing typed.

`hack/inject-appliance.sh` therefore sets GRUB `superusers` with a password generated at build time and **discarded**. Nothing can authenticate against it, which is the intent: the security model already says the break-glass credential is injected out of band rather than baked in, and an appliance-wide password shipped inside a public image is not a secret. Setting `superusers` closes all three surfaces at once — GRUB then demands authentication for entry editing, for the command line, and for every menu entry not explicitly marked `--unrestricted`, which covers the two recovery entries. Those entries are left in place rather than deleted, because `grub_update.py` re-renders `50-vyos-options.cfg` from its template on a structure migration and a deletion would not survive it; the lock does.

The half that is easy to get wrong is that `superusers` restricts the *normal* boot entry too, and upstream's `grub_vyos_version.j2` renders it without `--unrestricted`, so the lock alone would leave the VM waiting at a password prompt on every boot. The entry is marked in both the place it is generated and the template a later migration re-renders it from. All of this was measured rather than reasoned about, in qemu against a real GRUB: with `superusers` and no `--unrestricted`, an untouched boot stops at `Enter username`; with the flag it boots straight through, while `e`, `c` and a restricted entry each still stop at `Enter username`. `hack/grub-unrestrict.bats` pins the two things that would fail open silently — the drop-in filename, since `grub_main.j2` sources only `*-autoload.cfg`, and the menuentry regex, whose line shape belongs to upstream.

What this does **not** do is narrow the RBAC. The tenant keeps `virtualmachineinstances/console`, `/vnc` and `virtualmachines/restart` on the gateway VM; the console simply no longer leads anywhere. Restart remains available and is a denial of service against the tenant's own router, which they can already delete outright. Scoping that grant is a platform-wide change (see the residuals).

## Cilium egressDeny — metadata and management ranges

A namespaced `egressDeny` `CiliumNetworkPolicy` on the gateway endpoint denies link-local `169.254.0.0/16` (which includes the cloud metadata endpoint `169.254.169.254`) plus any operator-supplied management/node ranges (`security.egressDenyCIDRs`). Cilium deny rules take precedence over allow rules regardless of policy scope, so this namespaced deny composes correctly with the tenant's allow-only baseline (which allows egress to the world) — the deny wins. What Cilium contributes here is bounding the gateway's own egress destinations by its endpoint identity, which is what the design claims and no more: it contains destinations, not identities asserted inside tunnel traffic, and because the tenant baseline is allow-only a namespaced policy can widen what the gateway reaches but never narrow it. The egressDeny adds the explicit link-local + management deny that identity alone does not cover. This is the first `egressDeny` in the repository — every other cozystack policy is additive allow-only with no default-deny.

## API-key handling — not tenant-readable

The VyOS HTTPS-API token is generated by the chart (`lookup`+autogen for reconcile stability) into a per-instance Secret that is deliberately RBAC-isolated: it is NOT in the ApplicationDefinition `secrets.include` list and NOT in the tenant dashboard Role, so tenant roles cannot read it — only the controller can. It is seeded into the first-boot configuration so the API is authenticated before it is reachable, and the VyOS API binds to the pod-network address only, with the management firewall as the compensating network control. The token (and the PSK) are redacted from every error surface: a VyOS `/configure` failure can echo the offending set-command back in its body, so the controller replaces both secrets with a placeholder before the message reaches an Event, a condition or a log.

## Deny-set validation — no cluster-blackholing remote

A tenant's declared `remoteCIDRs` must be disjoint from cluster-owned addresses, or the namespace return route would blackhole or intercept cluster traffic. A pure `denyset.Validate` helper rejects any `remoteCIDR` that overlaps the pod / service / join networks, live node Internal/External IPs, allocated LoadBalancer/external service IPs, the always-reserved link-local (`169.254.0.0/16`) and loopback (`127.0.0.0/8`) blocks, or is a default route (`0.0.0.0/0`), or is not IPv4 (Phase 1 is IPv4-only). Node and service addresses are represented as `/32`, so a broader tenant subnet containing one is rejected by prefix overlap. The same discovery and validation code runs at admission and reconcile time: admission returns a synchronous `Forbidden`; reconciliation records an `InvalidRemoteCIDR` Warning Event and withdraws any routes that became unsafe after a topology change. Pod/service/join CIDRs come from the `cozy-system/cozystack` ConfigMap with platform defaults as fallback, while Nodes and Services are read live.

### What the deny set does and does not judge

Three fields program the gateway, and all three go through `denyset.Validate`: `remoteCIDRs`, `staticRoutes[].destination` and `bgp.neighbors[].address`. The last one matters beyond routing, because `renderBGPFirewallAccept` writes an input-filter accept for TCP 179 from that address, so an unjudged neighbour would open the management chain for an address the same value would have been refused in `remoteCIDRs`. A rejection names the field it came from, because the same address is legal in one field and refused in another.

Deliberately **not** judged: `staticRoutes[].nextHop`. It is the gateway's own next hop rather than a destination, so a cluster-owned value there misdirects this tenant's egress instead of intercepting anyone else's traffic, and the forward default-deny still bounds what is relayed. It is listed here rather than left implied, because a guard that covers most of a subsystem reads as covering all of it.

## Residuals (deferred to follow-ups)

These are the known gaps the Phase-1 boundary accepts by decision. Each is tracked in `followups.md`.

- **Boundary B is not fully realised.** Cilium allow rules are additive, so the tenant baseline's broad allow-external/internal-communication ingress still reaches the gateway endpoint alongside the gateway-ingress policy. Fully closing it would require excluding the gateway endpoint from the tenant baseline — a shared `packages/apps/tenant` change with broad blast radius. In Phase 1 the guest VyOS firewall (Boundary A + the local-input management drop + the forward-chain guards) is the real backstop for the management API and the tunnel; the gateway CNP is the pod-boundary layer on top, not the sole defence.
- **`port_security` is fully relaxed, not scoped.** kube-ovn v1.15.10 cannot express a CIDR in allowed-address-pairs, so the gateway port loses OVN anti-spoof entirely and the guest source filter carries the load. Scoped relaxation is a tracked follow-up pending upstream kube-ovn CIDR-AAP support; the guest source filter and its negative tests stay regardless.
- **A tenant super-admin can rewrite the gateway VM.** `cozy:tenant:super-admin:base` grants `kubevirt.io virtualmachines` with verb `*`, bound in every tenant namespace, so the boot disk and the cloud-init seed of a platform-owned appliance are editable by that tier. Flux drift correction is off, so the edit persists. This is not specific to site-router — the same tier can relax `port_security` on any VM it owns, since `kubeovn-webhook` only supplies the annotation when the pod did not set one — but site-router is the case where the relaxed port and the platform-owned guest coincide, which is why it is recorded here rather than left to the general statement. Closing it means either taking the gateway VM out of the tenant namespace or carving the kind out of that grant, both of which are the same platform-wide change as the console item below.
- **The tenant keeps console RBAC on a platform-owned VM.** `cozy:tenant:use:base` grants console, VNC and power on every VMI in the tenant namespace, with no `resourceNames`, because Kubernetes RBAC cannot scope a subresource by label or by owner and has no deny rules. The bootloader lock removes what that console was worth here, but the grant itself is wrong in principle for an appliance the tenant is not meant to administer, and it is not specific to site-router — every platform-owned VM in a tenant namespace inherits it. Narrowing it means dropping the blanket rule and having each VM-creating chart grant console on its own VMs by name, which is a change to every tenant's RBAC and needs a controller for the CAPK-generated names that `resourceNames` cannot wildcard. Tracked separately.
- **PSK is plaintext at rest.** The pre-shared key lives in a tenant-namespace Secret (base64 in etcd, not encrypted beyond whatever etcd encryption the cluster has) and is rendered into the guest VyOS configuration in plaintext. It is redacted from error surfaces, but the at-rest plaintext trade-off is inherent to a PSK-authenticated IPsec tunnel in this model.
- **The API key is seeded at first boot.** The token is baked into the first-boot configuration so the API is authenticated before it is reachable. A controller-namespace key with post-boot rotation to a value that never appeared in the seed is a documented enhancement, matching the reference implementation's acknowledged trade-off.
- **Negative-security acceptance needs a runtime e2e proof.** The guard *structure* (source filter, forward default-deny, IPsec-match jump, Boundary-A drop, MSS clamp, forced encapsulation) is implemented and unit-tested, and its VyOS leaf syntax — the `firewall ipv4 {input,forward} filter` / `firewall ipv4 name <NAME>` family and the `ipsec match-ipsec-in` / `ipsec match-none-in` matchers — is validated live against the shipped image (a full render-equivalent config commits cleanly). What is still deferred is the runtime proof on a booted two-VM topology that an undeclared-source packet, and a valid-source/world-destination packet, are both actually dropped; that is the e2e negative-security suite, blocked on the published appliance image (see `followups.md`).
